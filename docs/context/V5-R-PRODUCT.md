# Win DP v5-R 브라우저 제품 검증

## 사전 등록

배포 후보는 WASM이 직접 생성한 Float32 DP Expert 은행 1개와 `winDPv5Decision`의 `endgame: "none"`이다. 기준은 같은 정책의 검증된 Float64 은행이다. 승리점수율(승 1, 무 0.5, 패 0)의 비열등성 한계는 0.5%p다. 제품용 독립 시드 묶음 9521에서 대응 표본 10,000쌍을 양쪽 선공으로 구성한다. 같은 시드와 좌석에서 정책을 바꿔 경기 결과의 차이를 비교하고, 쌍을 단위로 단측 95% 신뢰구간을 산출한다. 하한이 −0.5%p를 초과할 때만 통과로 판정한다. 행동 불일치 수, 해당 행동의 Float64 가치 차이, 승/무/패, 원시 경기 자료와 측정 환경을 함께 남긴다. 중간 결과를 근거로 표본 수나 한계를 변경하지 않는다.

브라우저에서 모델을 기본 적용하려면 별도로 저사양 모바일 실측, 백그라운드 재개, 저장소 손상/할당량 초과와 반복 대국을 검증한다. 사용자 기기에서 모델이 실패할 경우 현재 기본 정책으로 폴백하고 기보에는 실제 실행 모델을 기록한다. INT16 포맷의 디코더가 현재 Float32로 확장하므로 그 파일 크기로 실행 메모리를 주장하지 않는다.

## 9521 결과

Node에서 동일 WASM 커널 및 DP 테이블로 독립 시드 10,000쌍(20,000경기)을 실행했다. Float32의 승리점수율 **50.000%**(9,922승·156무·9,922패), 쌍별 편차가 관측되지 않아 사전 등록 근사 단측 95% 하한 **0.000%p**로 비열등성 조건을 통과했다. 첫 100쌍의 실제 국면 13,807개에서 판단 54개가 달랐고 원본 가치 손실 10⁻⁶ 초과는 0개였다. 최대 Float64 가치 차이는 8.88×10⁻¹⁶이었다. 이는 해당 표본과 평가 목적의 결과다. [원시 경기와 측정 자료](../../training/results/product/v5-r-f32-9521.json.gz) · [재현 코드](../../scripts/product/v5r-noninferiority.ts)

| 후보 | 은행 본문 | WASM 선형 메모리 | WASM 생성 | 판단 평균 |
|---|---:|---:|---:|---:|
| Float32 | 142.1 MiB | 146.3 MiB | 3.06초 | 0.0686 ms |
| Float64 | 284.2 MiB | 288.4 MiB | 6.45초 | 0.0718 ms |
| INT16 YPB1 디코딩 | 73.3 MiB 저장 / 142.1 MiB 펼친 본문 | 미사용 | 디코딩 462 ms | 0.0630 ms, 2,000국면 |

WASM 수치는 선형 메모리이며 브라우저 프로세스 최대 RAM은 아니다. INT16은 검증용 비교이며 실행 시 전체 Float32로 펼쳐진다. 디코딩에는 두 본문의 합계 약 215.5 MiB와 별도 뷰·인덱스가 필요하다. 상태별 Uint16 직접 계산 또는 LRU는 이 버전에서 채택하지 않았다.

## 제품 시험 경로

`?ai-model=v5-r#play-setup`으로 이 탭의 매우 어려움에서 시험하고 `?ai-model=standard`로 되돌린다. 워커가 OPFS 캐시를 검증하고 필요할 때만 은행을 WASM으로 직접 생성한다. Web Locks를 지원하는 환경에서는 같은 버전을 두 탭에서 처음 열어도 한 번만 생성하고 다른 탭은 검증된 캐시를 복원한다. 계산 취소, 워커 오류 또는 시간 제한에 도달하면 해당 경기의 남은 AI 행동을 v4-D로 수행한다. 기보의 행동별 `decision.execution`에 실제 모델 ID·버전을 기록한다. 물리적인 저사양 모바일 검증 전에는 기본 매우 어려움이 계속 v4-D를 사용한다. 서버 고성능 AI는 향후 Pass 후보이며, 이 릴리스에 서버 연산이나 결제를 포함하지 않는다.

## Chromium 브라우저 검증

로컬 프로덕션 빌드에서 Web Locks 적용 후 데스크톱 Chromium의 첫 초기화는 11.29초, OPFS 복원은 974ms였다. 같은 호스트의 Pixel 7 에뮬레이션에서는 각각 10.62초, 486ms였다. 각 브라우저에서 서로 다른 탭을 동시에 준비해 단일 생성과 캐시 복원을 확인했다. 이 시간에는 DP 표 로드, 은행 뷰 생성과 캐시 검증, 첫 초기화의 저장이 포함된다. 여러 로컬 테스트를 동시에 실행한 환경의 단일 샘플이다.

오프라인 복원 뒤 AI 차례가 진행되었다. 캐시를 손상시킨 시나리오에서는 체크섬 검증 후 재생성했다(데스크톱 10.59초, Pixel 7 에뮬레이션 20.17초). 별도 Chromium 시험에서 24 MiB 저장소 한도와 초기화 중 탭 동결·복귀를 적용해 WASM 실행을 유지했다. 확장 워커 스크립트 로드를 차단하면 v4-D가 실제로 진행했고, 내보낸 기보도 v4-D로 기록했다. 물리적인 저사양 기기의 브라우저 프로세스 최대 RAM과 OS 백그라운드 복귀는 후속 검증이 필요하다.

## 추가 실행 검산

별도 Linux Node 프로세스에서 관측한 전체 최대 RSS는 직접 생성 Float32 337.4 MiB, Float64 481.2 MiB, INT16 YPB1을 Float32로 펼친 경로 392.1 MiB였다. 이 관측에는 Node 런타임, 주사위 커널, 상태별 뷰와 측정 과정이 포함된다. WASM 선형 메모리나 실기기 브라우저의 최고 메모리와는 각각 별개다.

캐시 없는 초기 설치 이후 네트워크를 끈 Chromium Pixel 7 및 iPhone 13 WebKit 에뮬레이션 각각에서 정적 WASM 자산으로 처음 은행을 생성하고 AI 턴을 마쳤다. Chromium의 같은 탭에서 4경기를 재대결로 이어 갔으며, 마지막 게임 리뷰까지 은행 한 개·워커 한 개로 처리했다. 실제 v5-R 판단 137건을 확인했다.

상태별 Uint16 직접 조회 및 양자화 전용 가치 계산은 더 적은 상주 메모리를 기대할 수 있으나, 기존 TypedArray 소비 경로의 계산 정밀도와 판단 시간 검증이 필요하다. 상태별 디코딩과 제한형 LRU는 반복 조회 패턴에 따라 실제 캐시 미스와 임시 할당을 검증해야 한다. 현재 제품 시험 경로는 Float64 전체 은행을 병행 생성하지 않는 직접 Float32 방식을 유지한다.

## Android·iOS 실기기 검증 절차

1. Android Chrome, iOS Safari에서 기기·OS·브라우저 버전과 PWA 설치 여부를 기록한다. 일반 URL에서 매우 어려움이 안정 모델로 시작하는지 확인한다.
2. [v5-R 시험 URL](https://oyueo-mm.github.io/YachtLab/?ai-model=v5-r#play-setup)에서 매우 어려움을 선택하고 AI 선공으로 시작한다. 캐시 생성과 다음 시작의 복원 시간을 각각 재고 가능하면 브라우저 또는 OS 도구로 프로세스 최대 메모리를 기록한다.
3. 은행 초기화 중과 AI가 한 차례 마친 뒤에 각각 앱을 백그라운드로 보내고 다시 연다. 화면이 복구되는지, AI가 계속 진행되는지, 탭이나 앱이 종료되거나 페이지가 다시 로드되는지 확인한다.
4. 같은 탭에서 두 경기 이상 이어 한다. PWA 설치 후 오프라인으로도 시작해 보고, 워커 실패나 폴백이 발생했으면 내보낸 기보의 `decision.execution` 모델과 버전을 확인한다. 실기기 메모리와 OS 복귀 결과를 기록할 때까지 기본 모델은 v4-D다.
