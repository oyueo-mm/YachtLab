## 1. CI/CD (D-061)

### 측정 (로컬 4코어 컨테이너, 현 main 빌드, Playwright 1.64 · Chromium headless shell)

| 구성 | 시간 | 결과 |
|---|---|---|
| workers=1 (기존 설정) | 1,473 s (24.6분) | 379 통과 · 53 조건부 건너뜀 · 0 실패 |
| workers=2 | 872 s (14.5분, −41%) | 기존 테스트 전부 통과(실패 10건은 이 브랜치의 새 테스트를 이전 빌드에 돌린 것) |
| workers=4 | 517 s (8.6분, −65%) | game-fx "연출 중 재대결" 1건이 CPU 경합으로 시간 초과(4코어에 브라우저 4개 + 서버) |

→ 한 러너에서 workers=4는 빠르지만 타이밍 테스트가 흔들린다. CI는 **샤드 4개 × workers=2**(러너마다 4 vCPU)로 나눠, 러너당 부하는 workers=2 수준으로 두고 전체 병렬도는 8로 올렸다. 예상: 브라우저 단계 ≈ 872 s / 4 ≈ 4분 + 설치·빌드 내려받기 약 1분, 전체 8~10분. 실제 CI 측정은 §1 끝의 표.

CI 실측(기존 단일 작업): Browser checks 23분 7초(run 45720000134), 전체 약 26분.

**병목(workers=1 파일별 합):** game-fx 362 s, app 146 s, game-flow 144 s, online 122 s, profile 108 s. 가장 긴 단일 테스트는 PPO 12라운드 완주(약 60 s ×2 프로젝트), 프로필 12라운드(58 s), 채팅 양방향(34 s), 3D 자원 누수(31 s).

### 새 파이프라인

```
scope(변경 파일 → docs | seo | full, 판별 불가 = full)
 ├─ unit (Vitest)            ─┐
 ├─ build (타입·테스트 빌드·Pages 빌드) ─┼─ browser ×4 샤드(각 workers=2, 데스크톱+모바일 프로젝트가 샤드에 고루 분산)
 └───────────────────────────┴─ ci-result(필수 작업 모두 success일 때만 통과) → deploy(main push만)
```

- **docs**: `docs/**`, 저장소의 `*.md`, deploy.yml 외 워크플로만 바뀐 경우. 사이트가 바뀌지 않으므로 빌드·브라우저·배포를 하지 않는다.
- **seo**: `public/` 정적 HTML·sitemap·robots·페이지 CSS만 바뀐 경우. 빌드 후 SEO·PWA 브라우저 검사만 하고 배포(목표 2~5분).
- **full**: 그 밖의 모든 경우. `training/`·`benchmarks/`는 앱·Vitest가 읽으므로 full이다. 분류 규칙은 `scripts/ci/classify-changes.mjs`, 단위 테스트 `tests/ci-classify.test.ts`.
- 같은 브랜치·PR의 새 push가 이전 실행을 취소한다. 매일 03:17 KST에 main 전체 회귀(배포 없음).
- 실패한 검증은 `ci-result`가 막고, `deploy`는 `ci-result == success`일 때만 실행된다. 롤백은 이전 커밋 재배포(`workflow_dispatch`).
- 테스트 간 공유 상태: 온라인 테스트는 파일마다 임의 포트의 wrangler/Node 서버를 띄우고(`tests/helpers/wrangler.ts` 포트 경합 재시도), 브라우저 컨텍스트를 테스트마다 새로 만든다. 파일 내부 순서 의존이 있을 수 있어 `fullyParallel`은 켜지 않고 파일 단위로 나눈다.
- 무료 러너: 공개 저장소의 표준 러너는 무료다. 동시 작업 수는 늘지만(최대 6개) 각 샤드가 짧아 대기 시간이 줄어든다.

## 2. 게임 화면 (D-060)

### 발견한 원인
- **점수판 스크롤**: `responsive.css`의 데스크톱 규칙이 점수판을 `max-height: calc(100dvh - 84px); overflow-y: auto`로 고정했다. 행 높이 43 px + "상단/하단" 구분 행 2개 + 두 줄 헤더로 1366×768에서 약 120 px가 넘쳤다. 구분 행을 숨기고 행 높이를 화면 높이에 맞춰(30~40 px) 줄였으며 글자 크기는 줄이지 않았다.
- **1366×768에서 페이지가 내려가 있던 문제**: 게임판 위의 요약 줄(아바타가 이름 위로 쌓인 2~3줄)과 이모티콘 줄이 보드를 아래로 밀었다. 두 줄을 보드 안 가장자리로 옮겼다.
- **채팅이 잘 안 보이던 문제**: 말풍선이 좌석 요약 *위쪽*(`bottom: 100%`)에 떠서 고정 헤더 밑이나 화면 밖으로 나갔다. PC에서는 요약 줄 자체가 숨겨지는 규칙(`items.css`)과 겹쳤다. 이제 보드 안 좌석 칩 바로 아래에 나타난다.
- **휴대폰 시트가 좁아지던 문제(이번 개편 중 발견)**: 위치용 `transform`이 있는 부모 안에서 `position: fixed` 시트가 부모 기준으로 배치됐다. `transform` 없이 가운데 정렬한다.
- **보상 카드가 홈 레이아웃을 깨던 문제**: `MatchRewards`가 홈 `main`의 형제 섹션으로 들어가 그리드 열을 차지했다. 화면 위에 떠 있는 토스트로 바꿨다. 보상은 서버 원장에 이미 기록되어 있으므로 닫거나 새로고침해도 중복 지급되지 않는다(조회는 GET만, 기존 테스트 유지).

## 3. 게임 리뷰 (미착수)
기존 리뷰(`src/review/`)는 판단 손실·굴림 운을 이미 분리해 계산한다([AI-REVIEW](./AI-REVIEW.md)). 이번 작업에서는 화면 재설계를 하지 않았다. 다음 작업 순서 제안:
1. 기보 타임라인을 1~12라운드 그룹(라운드 안에 굴림·킵·기록, 두 선수 색 구분)으로 바꾸고 ←/→, Home/End, Space(자동 재생) 단축키.
2. 결과 팝업과 기본 리뷰 상단에 정확도·운 점수(기존 정의 재사용, 좋음/보통/나쁨)와 좌석 색.
3. 운 점수: 기존 `luck`(행동 후 기대가치 − 굴림 전 기대가치 누적)을 그대로 쓰고, 기권·미완료 경기는 평가 범위를 표시.

## 4. 비회원 상점 (D-063)
- 상품 목록·가격·설명·등급·미리보기·강화 단계·시즌 상품·뽑기 확률은 로그인 없이 본다. 시즌 판매 기간은 서버 시간을 모를 때 기기 시간으로 표시만 한다(구매는 서버가 다시 검사).
- 구매·뽑기 버튼을 누를 때만 로그인 팝업. "Google로 로그인"은 현재 탭·필터·열려 있던 상품·스크롤을 `sessionStorage`(20분)에 저장하고 기존 로그인 흐름을 시작한다. 돌아오면 같은 화면을 열고 최신 잔액·가격으로 상품 상세만 다시 연다. **자동 구매·차감 없음**, 구매는 기존 확인 대화상자와 요청 ID(멱등)를 그대로 쓴다.
- 슬롯 확장·인벤토리(장착·강화)는 기존처럼 로그인 안내.

## 5. 관리자 통계 (설계, 미구현)
요구한 지표 대부분은 서버 이벤트가 필요하다. 무료 인프라(Workers Free·Durable Objects SQLite)를 고려한 설계:

| 역할 | 도구 | 이유 |
|---|---|---|
| 방문·페이지뷰·유입 경로·Core Web Vitals | **Cloudflare Web Analytics**(무료, 쿠키 없음) 또는 GA4 | Pages 정적 사이트에 스크립트 한 줄. Cloudflare는 개인정보 수집이 적고 동의 배너 부담이 작다. GA4는 퍼널·코호트가 강하지만 쿠키·동의 문제가 있다. |
| 게임 행동 퍼널·CCU·경기·경제 | **자체 Worker 이벤트**(일별 집계 DO) | 서버가 이미 아는 사실(매칭·경기 완료·정산·원장)을 서버에서 한 번만 센다 → 클라이언트·서버 중복 집계 방지. |

- 이벤트: `visit`(클라이언트, 하루 1회/기기 해시 없이 무작위 ID), `game_start`, `game_finish`, `online_try`, `online_finish`, `signup`, `purchase`, `invite_open`. 서버가 아는 이벤트는 서버만 기록.
- 저장: KST 날짜별 카운터와 HyperLogLog 대신 하루 단위 무작위 방문 ID 집합(최대 N개, 초과 시 샘플링 표시). 원시 이벤트는 30일 보존.
- 관리자: 기존 `ADMIN_TOKEN` 시크릿을 서버에서 검증(이미 관리자 API 존재, 미설정 시 404). 테스트·관리자 트래픽 제외 플래그, CSV 내보내기.
- 금지: IP·채팅 내용·이메일 저장, 가짜 수치.
- **사용자 설정 필요**: Cloudflare Web Analytics를 쓰려면 Cloudflare 대시보드 → Web Analytics → 사이트 추가(`oyueo-mm.github.io`) → 발급된 `token`을 알려 주면 `index.html`과 정적 페이지에 스크립트를 넣는다. GA4를 쓰려면 측정 ID(`G-…`). 관리자 통계를 쓰려면 Worker 시크릿 `ADMIN_TOKEN` 등록.

## 6. UTM (D-065)
- `?utm_source=…&utm_medium=…&utm_campaign=…&utm_content=…`를 첫 방문(first)·최근(last)으로 이 기기 `localStorage`에 저장하고 주소창에서 지운다. `?room=` 초대 코드는 유지되므로 UTM이 붙은 초대 링크도 방 입장 화면을 연다(브라우저 테스트).
- 값은 문자·숫자·`_.-+ ` 80자로 제한. 아직 어디에도 전송하지 않는다(§5 이벤트가 생기면 첨부).
- 링크 생성: `campaignUrl()`(방 코드 유지). 관리자 화면의 링크 생성기·QR·캠페인별 지표는 §5 이후.
- 결과 공유 링크는 `utm_source=share&utm_medium=result_card`.
