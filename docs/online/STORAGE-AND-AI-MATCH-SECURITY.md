# 온라인 저장 쓰기 절감과 서버 검증 AI 대전 보안 분석 (2026-11-24)

> 상태: **연구·설계. 서버 코드는 바꾸지 않았다.** 유료 플랜 전환·신규 유료 리소스 생성 없음.
> 실측 근거: `scripts/economy/measure-room-writes.ts` → `docs/economy/results/room-writes.json`. 용량 계산: [FOLLOWUP-GENERATED §14](../economy/FOLLOWUP-GENERATED.md).

## 1. 현재 저장 구조(코드 확인)

- 방마다 Durable Object 1개(`YachtRoom`), SQLite 테이블 `room(id INTEGER PRIMARY KEY, record TEXT)`에 **한 행**만 쓴다(`worker/src/index.ts`). 명령이 받아들여질 때마다 레코드 전체를 UPSERT → **명령 1개 = 행 쓰기 1회**(INTEGER PRIMARY KEY라 인덱스 행 추가 없음).
- 저장되는 명령: 방 생성, 입장, 시작, **굴림(roll)**, **점수(score)**, 기권·재대결 등. 저장 안 되는 것: 고정(hold) 표시(소켓 첨부), 채팅·이모티콘, 관전, 핑, 인증 전 메시지.
- 알람: 턴 제한·인증 시간·정리를 알람 1개로 처리하고 **더 이른 시각으로 옮길 때만** `setAlarm`(1회 = 행 쓰기 1회).
- 전역 `RoomDirectory`: 방 생성 시 `rooms`(TEXT PRIMARY KEY → 테이블 행 + 자동 인덱스 행 = 2) + `daily` UPSERT(1) = 약 3, 정리 시 삭제 2.
- 저장은 **응답 전에** 끝난다(fail-closed, D-020): 주사위 결과는 저장된 뒤에만 플레이어에게 보인다.

## 3. 서버 권위·경기 복구를 유지하면서 쓰기를 줄이는 방법

| 안 | 내용 | 경기당 쓰기 | 위험 | 판단 |
|---|---|---|---|---|
| A 현재 | 굴림·점수마다 저장 | 약 110 | 없음(기준) | 유지 가능 |
| **B 턴 첫 굴림 병합** | 턴의 첫 굴림은 선택이 없으므로, 점수 기록(턴 종료)과 **같은 쓰기**에서 다음 플레이어의 첫 굴림까지 확정·저장. 화면은 "굴리기" 버튼을 누를 때 공개(이미 저장된 값) | 약 87(−21%) | 첫 굴림 값이 서버에 먼저 정해짐 — 클라이언트에 보내지 않으면 정보 노출 없음. 턴 제한 시간 계산 시작점만 조정 | **권장(다음 서버 작업 후보)** |
| C 턴 내부 상태를 소켓 첨부에 | 턴 시작에 비밀 턴 시드만 저장하고, 턴 안의 굴림 상태는 두 플레이어 소켓 첨부(서버 측, 쓰기 0)에 둔 뒤 점수 때 저장 | 약 40(−64%) | **분기(branch) 공격:** 모든 소켓이 끊기고 객체가 퇴출되면 턴 시작으로 되돌아가는데, 플레이어는 이미 본 굴림 결과를 알고 다시 고를 수 있다. 결정적 주사위 유도(시드+굴림 번호+위치)는 "본 값"을 재현하므로 정보 이득이 생긴다. 상대 소켓이 열려 있으면 보통 보존되지만 운영 재시작(배포)·장애 때 깨짐 | **연구 후보만** — 공정성 검증 전 채택 금지 |
| D 굴림 묶음 저장 | 여러 굴림을 모아 한 번에 저장 | — | 저장 전에 결과를 보여주면 fail-closed 위반(되돌리기 시 결과 선별 가능) | **기각** |
| E 레코드 압축 | 행 크기 축소(현재 최대 약 22KB) | 변화 없음 | 쓰기 "행 수" 과금이라 효과 없음(저장 용량만 감소) | 부차적 |
| F 알람 재설정 감소 | 이미 "더 이를 때만" 재설정 | 약 7 → 5~6 | 거의 없음 | 소폭 |

결론: **B로 약 20% 절감**이 공정성 위험 없이 가능한 최대치에 가깝다. 그 이상(C)은 "보여준 값은 반드시 먼저 저장" 원칙을 깨야 하므로 권장하지 않는다.

## 4. 무료 플랜에서 가능한 최대 운영 규모

- 행 쓰기 무료 10만/일은 `ideadock-auth`와 공유(D-022). YachtLab 몫을 50·70·100%로 두고 계산.
- 경제 처리 쓰기: 보상 경기 1회당 계정 DO에 지갑·진행·원장을 **한 트랜잭션 2행**(원장 행 + 지갑 행)으로 설계하면 2, 분리하면 3.
- 하루 PvP 경기 상한(몫 70%, 경제 2쓰기): A 약 610, B 약 770, C 약 1,550 — 수치는 [FOLLOWUP-GENERATED §14](../economy/FOLLOWUP-GENERATED.md).
- **현재 `DAILY_ROOM_LIMIT` 300은 행 쓰기 기준으로는 여유가 있다**(A·경제 포함 약 3.4만 쓰기 = 무료 10만의 34%, 70% 몫의 49%).
- **DO 실행 시간이 더 먼저 닿을 수 있다:** 무료 13,000 GB-s/일(D-021 기록값), 객체당 128MB 과금. 메시지 간격이 짧아 경기 내내 깨어 있으면 경기 약 6분 20초 = 47.5 GB-s → **하루 약 270경기**. 절반만 깨어 있으면 약 550경기. 현재 300 한도와 비슷한 수준이므로, 매칭·경제 도입 전에 **대시보드의 Duration 실측이 최우선**이다(이 세션은 대시보드 접근 없음).
- DAU 환산: DAU 1명이 하루 PvP 2경기면 300경기 = DAU 300, 8경기면 75. 신규 사용자 수·DAU·플레이어-경기·경기를 섞지 않는다(1경기 = 플레이어-경기 2).

## 5. 서버 검증 AI 대전의 어뷰징 위험

AI 대전은 상대가 사람이 아니므로 "상대 소켓이 열려 있어 상태가 보존된다"는 안전장치가 없다. 후보 설계별 위험:

| 공격 | 서명 상태(무상태 Worker) 방식 | 메모리 전용 DO(저장 없음) | 저장 DO(PvP와 동일) |
|---|---|---|---|
| **서명 상태 재사용(replay)** — 예전 서명 상태를 다시 보내 다른 선택 | 서버가 "사용됨"을 기억하지 않으면 막을 수 없음(기억하려면 쓰기 필요) | 해당 없음 | 해당 없음 |
| **분기(fork)** — 같은 상태에서 다른 고정으로 여러 번 굴려 결과 비교 | 결정적 주사위면 미래 값이 드러남, 비결정적이면 원하는 결과 선택 가능 → **치명적** | 객체 하나가 순서대로 처리 → 불가 | 불가 |
| **재전송** — 같은 명령 반복 | 멱등 키 필요 | 명령 ID 멱등(현 구조 재사용) | 현 구조로 차단 |
| **주사위 결과 선별(abort-to-reroll)** — 불리하면 끊고 새 경기 | 시작 횟수 제한 필요 | 퇴출·끊김 시 경기 무효 → 끊고 다시 시작해 "좋은 첫 굴림"을 낚을 수 있음 | 재접속으로 이어짐(낚시 불가) |
| **행운 업적 낚시**(첫 굴림 요트 등) | 위와 같음 | 시작만 반복하면 첫 굴림 확률 시도 증가 | 완료 경기만 집계하면 무의미 |
| AI 결정 조작 | AI는 서버가 계산해야 함(클라이언트 계산 금지) | 서버 계산 | 서버 계산 |
| 미래 주사위 예측 | 시드·RNG 상태를 클라이언트에 주면 예측 가능 | 서버 비공개 | 서버 비공개 |

권고:
1. **서명 상태(무상태) 방식은 기각** — 재사용·분기를 막으려면 결국 저장이 필요하고, 그러면 저장 이점이 사라진다.
2. AI 대전은 **PvP와 같은 저장 DO**(fail-closed)를 기본으로 하되, 쓰기를 줄이려면 §3-B를 똑같이 적용.
3. 보상·퀘스트·업적은 **완료된 경기만** 집계. **시작한 경기 수**로 하루 한도를 차감(끊고 다시 시작하는 낚시 차단). 중도 이탈은 패배 처리, 완료 보상 없음.
4. AI 대전은 연승·랭크 업적 제외(쉬운 AI 상대로 연승 농사 방지), 보상은 PvP보다 낮게(정수안: 완료 7).
5. 난이도 선택형이면 **쉬운 AI 승리**의 가치가 낮으므로 승리 보너스는 PvP의 절반 이하. "매우 어려운 AI 승리" 퀘스트는 보류(합의).
6. Workers Free CPU 10ms/요청 제한: AI 결정을 서버에서 계산하므로 DP 테이블(2MB) 로드·턴당 계산 시간을 측정해야 한다. DO는 메모리에 테이블을 유지할 수 있지만 첫 로드 비용 확인 필요.
