## A6 클라이언트 계약

`useBackgroundMatch(server, onMatched)`는 App에 한 번 장착한다. 하위 UI는 `MatchController`를 받아 사용한다. `MatchPopup`은 최소 구현이며 `state`, `display`, `setDisplay("hidden" | "minimized" | "expanded")`, `start(name)`, `cancel()`, `reconnect()`가 표현 레이어의 진입점이다. 페이지 컴포넌트가 별도 소켓을 시작할 필요가 없다.

| 상태 | 전환 조건 |
| --- | --- |
| `idle → connecting` | 빠른 대전 시작 또는 같은 탭의 티켓 복구. 중복 클릭은 기존 요청을 사용한다. |
| `connecting / reconnecting → waiting` | 서버가 `queued{since,waiting}` 확인. 표시 시간의 기준은 `since`다. |
| `waiting → pairing` | 서버의 `check`에 브라우저가 자동 `ready` 응답하고, 허브가 후보 소켓의 응답을 확인해 방 할당 시작. 체크에서 실패한 상대는 제외하며 남은 대기자 순서를 유지한다. 연결 확인 창은 최대 4초다. |
| `waiting / connecting → cancelling` | 취소 요청을 전송하거나 재접속 시 전달. 서버가 `cancelled`를 확인하면 `idle`. 이미 할당을 시작했으면 같은 배정 결과를 처리한다. |
| `matched → entering` | 서버의 `matched`를 받은 탭이 좌석을 저장하고 자동 이동. 여기서 `yachtlab-match-found`가 `{code, opponent}`로 한 번 발생하고 알림음을 재생한다. 상태 두 개는 한 렌더로 합쳐질 수 있다. |
| `entering → idle / error` | 룸 `welcome`이면 `entered()`. 치명 오류 또는 20초 동안 인증된 룸 입장 응답이 없으면 `entryFailed(message, room)`. 해당 좌석으로 재입장할 수 있다. |
| `* → error` | `DUPLICATE`, `SESSION_EXPIRED`, `EXPIRED`, `IN_MATCH`, `UNAVAILABLE`, `NETWORK`, `REPLACED`, `ENTRY_FAILED` 등. `NETWORK`는 남은 티켓으로 `reconnect()`. |

`offerAfterMs`는 오프라인 AI 안내의 UI 입력값이다. **기본안은 대기 30초 이후 안내**(D-094)이고, 안내를 따라가도 매칭은 계속된다. 별도 수락/거절 버튼은 없다. 매칭 성공 후 3초 카운트다운은 **A6 구현 범위**이며 C3에는 두지 않았다(현재 즉시 자동 입장). 최종 매칭 팝업 디자인과 관전 목록 UI도 A6 범위다. 서버 AI는 대기 시작 화면에서 접힌 별도 메뉴로 접근한다.

중단된 로컬 게임과 경제 화면은 같은 컴포넌트 인스턴스를 유지한다. 매칭 때문에 가려진 로컬 AI 작업은 취소하고 상태를 보존한 채 복귀할 때 재개한다. 경제 요청의 서버 결과와 요청 후 화면 상태를 유지한다. 리뷰는 모달을 내릴 때 C2 분석 취소·Worker 정리를 그대로 실행한다. 복귀 시 같은 리뷰와 선택한 행동 위치를 복원하고 완료 캐시를 재사용한다. 관전은 페이지 이탈 시 기존 소켓을 닫으며 기존 관전은 자동 재연결하지 않는다. 실제 새로고침은 티켓과 저장 좌석 복구만 지원한다.

## 서버와 구버전 호환성

- `GET /api/features`의 선택 플래그는 `backgroundMatch`, `activity`, `friendPublicSpectate`다. 기존 빠른 대전 플래그만 있으면 WebSocket 레거시 큐를 사용한다. 이 경우 전역 탐색은 가능하지만 v2 취소 확인·준비 확인·할당 경합 응답은 지원 범위가 기존 Worker 수준이다. `quickMatch`가 없는 Worker 및 로컬 Node 서버에서는 친구 대전 진입점을 사용한다. 새 현황 API는 플래그가 있을 때만 호출한다.
- `/ws/match`의 `queue`는 `name,ticket,device,session?,v?`를 받는다. `v:2`에서 서버 `check{id}`에 `ready{id,session?}`를 자동 응답한다. 연결이 끊긴 취소는 `cancel{v:2,ticket,session?}`로 재접속해 확인한다. 15초마다 `alive`, 미응답 45초 및 최대 대기 5분은 기존 기준이다. 연결이 짧게 끊기면 허브 메모리의 기존 대기 순서를 이어간다. 허브 재시작 전에 끊긴 소켓의 대기 순서는 초기화될 수 있다. 사용자·기기 해시·티켓을 중복 검사하며, 기존 브라우저 저장소로 식별할 수 없는 게스트가 여러 모드에 접속하는 경우는 계정 수준 중복 방지를 적용할 수 없다.
- 방 할당 시작 전 허브가 시도 ID, 좌석 순서와 자격 증명을 기록한다. 디렉터리는 같은 ID에 같은 방 코드를 반환하고 룸은 서버가 제공한 동일 좌석 토큰으로 재시도를 검증한다. 허브는 두 결과와 대기 잠금 변경을 한 SQLite 트랜잭션에 반영한다. 결과와 미확정 시도는 최대 5분 동안 검색 가능하다. 룸 정리 알람과 디렉터리 보존 기한은 기존 값이다. 디렉터리가 새 경기의 회원 좌석을 예약하므로 친구·빠른 대전·서버 AI의 동시에 시작하는 경기는 충돌로 거절한다. 업데이트 이전부터 시작한 경기에 대한 회원 좌석 예약은 소급하지 않는다.
- **친구 대전 관전 범위(D-095).** 방장이 `private`(기본, 외부 관전 불가) · `invite`(링크 관전: 관전 전용 링크를 가진 사람) · `public`(공개: 관전방 목록에서 누구나) 중 하나를 고른다. 소켓 메시지는 `spectate{allow, visibility?}`이고 **서버가 방장인지 검사**한다(방장이 아니면 `error NOT_HOST` + 현재 상태). 구버전 페이지의 `{allow:true}`는 방장일 때 `invite`, `{allow:false}`는 `private`이다. `spectate` 상태는 `visibility`(유효 범위), `hostControl:true`, `host`(방장 playerId), `sid`(관전 ID, 범위가 켜져 있을 때), `key`(링크 키)를 주고, `allow`는 모든 좌석에 유효 범위를 그대로 비춰 구버전 페이지의 스위치가 실제 상태를 보이게 한다. 일반 참가자는 패널에서 현재 범위를 읽기 전용으로 보고, 범위가 바뀌면 모든 참가자에게 6초간 상태 안내("방장이 관전 범위를 '…'(으)로 바꿨어요.")를 띄운다. 방장 승계·이양 시 범위는 방 기록에 남아 유지되고 새 방장만 바꿀 수 있다. 대기실에 새 참가자가 들어와도 방장이 정한 범위는 유지된다.
- **키 관리.** 링크 키(`key`)와 공개 목록 키(`publicKey`)를 분리했다. 범위를 넓히면 새 키를 발급하고(넓히기는 방 단위 1초 간격 제한), 좁히면 즉시 처리한다: `public→invite`는 공개 목록 키와 그 관전자만 폐기(링크 관전자는 유지), `→private`는 두 키와 모든 관전자를 폐기한다. 다시 열면 이전 링크는 동작하지 않는다.
- **경기 종료·재대결(D-027 유지).** 친구 경기가 끝나도 범위와 키를 유지해 관전자가 최종 결과와 같은 방 재대결을 이어서 본다. 공개 목록에서는 종료 즉시 빠지고(`publicEntry`는 `playing`만), 목록 키 발급도 멈춘다.
- **호환성.** 방장 제어 이전에 저장된 방(`spectate.mode` 없음, 구 Worker 기록)은 기존 규칙을 그대로 읽는다: 모든 좌석이 허용했을 때만 링크 관전, 새 참가자가 앉으면 꺼짐, **공개는 소급 부여하지 않는다**(C3 초안의 `publicAllow`는 무시). 새 페이지가 구 Worker(`hostControl` 없음)를 만나면 기존 참가자별 스위치를 그대로 보인다. C3 초안의 `preferences`는 배포된 적이 없어 제거했다.
- **관전 ID 분리(PR118-01).** 관전 링크와 공개 목록은 방(=초대) 코드 대신 10자 관전 ID(`sid`, 방 코드 알파벳, 6자 코드와 구분)를 쓴다. 링크 형식은 `?watch=SID&k=KEY#spectate`, 소켓은 `/ws/SID`. Worker는 디렉터리 DO의 `spectate_ids(sid → code)` 행(방당 1행, 방 삭제·6시간 정리와 함께 제거)으로 찾고, Node 서버는 메모리의 방에서 찾는다. `GET /api/spectate/rooms` 항목은 `id`(=`code`, 구버전 페이지 호환을 위해 같은 값)·`kind,status,participants,players,round,rounds,spectators,max`이며 방 코드는 들어가지 않는다. `POST /api/spectate/:id/watch`는 관전 ID로만 받아 `{id, code:id, key}`를 돌려준다(방 코드로 부르면 404). 관전자에게 가는 `watching.code`도 관전 ID다. 관전 키는 `hello{token}`으로 좌석이 되지 않고(4001), 관전 ID로는 `/api/rooms/:id/join`이 404다. 구버전 페이지가 만든 `?watch=CODE` 링크와 `/ws/CODE` 관전은 호환을 위해 계속 받는다(그 링크는 원래 코드를 담고 있었다).
- `GET /api/activity`의 `ServerActivity`는 `asOf`(서버 Unix ms), `timezone:"UTC"`, `waiting`, `playing`(random/friend/ai), `privatePlaying`, `spectators`, `completedToday`, `yachtsToday`, `activeUsers`다. 모든 라이브 방의 이벤트를 관측하지 못한 경우 방·관전자 집계는 `null`이다. 활성 사용자는 게임 밖 활동까지 포함한 사이트 전체 계정·게스트 수를 의미하므로 `null`로 반환한다. 관전자 수의 단위는 권한을 얻은 연결이며 사용자 수와 합산하지 않는다. 대기는 허브의 생존 신호와 만료 조건을 충족한 대기 티켓이다.
- UTC 일자별 당일 완료는 정상 종료 이벤트의 경기 ID, 요트는 서버의 양수 `yacht` 점수 이벤트의 경기 ID·시퀀스로 중복 제거한다. 로컬 오프라인 경기, 몰수 종료 및 채점되지 않은 주사위 조합은 포함하지 않는다. Worker 버전 교체 이전에 전달되지 않은 이벤트와 전달 실패 후 룸이 정리된 경우에는 집계가 누락될 수 있다. 이 응답의 데이터는 운영 관측용이며 정산의 입력으로 쓰이지 않는다.

## 갱신과 Free 플랜 영향

새 Worker 리소스나 바인딩은 없다. 대기 중에는 기존 15초 WS 생존 신호를 쓰며 대기 티켓을 SQLite에 쓰지 않는다. v2 후보당 브라우저별 자동 응답 한 건과, 회원 후보의 세션 재검증 한 건이 추가된다. 새 배정의 핵심 SQLite 쓰기는 두 명 기준으로 허브 시도 1행, 식별자 잠금 최대 6행의 초기 및 확정 쓰기, 수령 정보 4행, 디렉터리 배정 1행 및 회원 좌석 최대 2행과 종료 정리다. 기존 경기당 약 110행 수준의 명령과 로그를 보존한다. 완료와 유효 요트는 관측 값마다 최대 한 행을 추가한다.

관전 화면이 보일 때만 기존 목록 조회 10초(응답 캐시 5초)와 현황 조회 30초를 사용한다. 연결한 관전자는 기존 WS로 갱신된다. 방은 상태/공개 범위/관전자 수 변경 시 익명 집계를 보내며, 공개 목록은 라운드·점수·관전자 수가 바뀔 때 갱신한다. 올바른 권한은 캐시가 아닌 룸에서 확인한다. 운영 요청량, CPU, 실기기 절전 제한은 측정되지 않았다.

### 현황 API 비용 (PR118-02)

| | 변경 전 | 변경 후 |
| --- | --- | --- |
| 요청당 전역 DO 호출 | 디렉터리 `liveCodes()` 1 + 허브 `activity()` 1 = **2회** (isolate·클라이언트당 분당 15회 제한만 있음) | isolate 메모리 캐시 적중 시 **0회**, 미적중 시 허브 1회. 허브는 디렉터리 조회를 `ACTIVITY_CACHE_MS`(기본 10초) 동안 재사용하고 동시 미적중 요청을 한 번의 조회로 합친다 |
| 전역 상한 | 요청 수에 비례 | 디렉터리 호출 ≤ 1회/10초(허브 하나), 허브 호출 ≤ isolate 수 × 1회/5초 |
| 데이터 최신성 | 요청 시점(브라우저 `max-age=15`) | 최대 약 15초(허브 10초 + isolate 5초), `max-age=10`. `asOf`는 집계 시각 |
| 새 리소스 | — | 없음(Cache API·KV·유료 기능 미사용, 메모리만) |

`ACTIVITY_CACHE_MS=0`이면 매 요청 새로 집계한다(테스트 전용). 실제 운영 요청량·CPU는 측정 전이다.

### 경기 참가 잠금 (PR118-03)

`playing_users`는 회원 계정의 동시 경기를 막는다. 해제 경로는 경기 종료(`releaseMatch`, 실패 시 방이 다음 이벤트·알람에서 재시도), 방 삭제(`release`), 디렉터리 6시간 정리(보존 기한이 지난 방)다. 해제가 계속 실패하면 계정이 방 정리 때까지 IN_MATCH로 막힐 수 있었다. 이제 IN_MATCH가 날 때 디렉터리가 **잠금을 가진 방에 직접 묻고**(`holdsAccount(userId, matchNo)`: 방이 살아 있고, 그 경기 번호가 진행 중이며, 해당 계정 좌석이 기권하지 않았는가), 방이 부인한 잠금만 조건부 삭제(같은 code·match_no일 때만) 후 한 번 다시 시도한다. 2분 미만의 잠금(방 생성 중)은 묻지 않고, 방에 묻지 못하면 잠금을 유지한다. **시간만으로 해제하지 않으므로 진행 중인 경기의 중복 참가는 열리지 않는다.** 같은 방 재입장은 원래대로 허용된다. 행에는 `at` 열을 추가했고 이전 행은 오래된 것으로 읽는다(스키마 이전은 멱등). 코드: `worker/src/reservations.ts`, 테스트: `tests/online-reservations.test.ts`. "이어하기/포기" 안내 UI는 A6 후보로 남긴다.


## 경계

단일 방의 실제 경기 규칙·보상·원장은 기존 엔진 및 정산을 사용한다. 서버 큐에서 양측 연결을 확인해도 DNS·네트워크 변경 등으로 룸 진입이 실패할 수 있다. 이 경우 좌석 재입장과 기존 온라인 재접속 유예를 사용한다. 브라우저 종료, OS 중지 동안 연결 유지와 새로고침 후 로컬 게임 복원은 지원 계약에 포함하지 않는다. 최종 팝업 및 관전 목록 디자인은 A6 범위다.

## C3.1 후속 요구사항 — **SOC-1에서 구현**([SOC-1 §3](./SOC-1-SOCIAL.md), D-126). 아래는 원래 기록.

친구 대전 대기실에 **준비 완료 / 이번 경기 관전 / 준비·관전 취소**를 둔다. 방 소속과 실제 경기 참가 상태를 분리한다.

- 관전을 고른 사람은 참가 인원과 준비 완료 조건에서 빠진다. 경기가 끝나면 모두 같은 대기실로 돌아와 다음 경기의 참가/관전을 다시 고른다.
- 방장도 관전할 수 있고 방장 권한(설정·시작·이양·외부 관전 범위)은 유지한다.
- 관전자에게 참가 보상, 승패, 전적을 주지 않는다. 경기 중 참가자↔관전자 전환은 금지한다.
- **외부 관전 범위(D-095의 private/invite/public)와 대기실 구성원의 내부 관전 권한은 별개**다. 외부가 비공개여도 구성원은 내부 관전할 수 있어야 하며, 내부 관전자는 외부 관전 키·ID를 받지 않는다.
- C3.1에서 검토: 대기실 최대 수용 인원(현재 좌석 수 = 수용 인원), 최소 참가 인원(2), 재대결 흐름(현재 "참가자 전원 요청")과의 관계, 기존 방 호환.

데이터 계약 후보(확정 아님):

| 항목 | 후보 |
| --- | --- |
| 방 기록 | `members: Record<memberId, { name, identity?, look, joinedAt }>`(방 소속) + 경기별 `roster: string[]`(실제 참가). 기존 `state.players`는 roster로 해석하고, `members`가 없는 기존 방은 players = members로 읽는다 |
| 대기실 상태 | `LobbyState.intent: Record<memberId, "ready" \| "watch" \| "idle">`, 기존 `ready`는 `intent === "ready"`의 투영으로 유지 |
| 클라이언트 메시지 | `{t:"intent", value:"ready"\|"watch"\|"idle"}`(대기실에서만, 경기 중 거절). 기존 `{t:"ready", ready}`는 `ready/idle`로 매핑 |
| 내부 관전 | 구성원 좌석 토큰으로 `hello` 후 `view.you = null`인 관전 뷰. 외부 관전 키·`sid`와 별개이며 외부 범위가 `private`여도 동작 |
| 시작 조건 | `roster = intent==="ready"`인 구성원(방장은 시작 시 참가/관전 선택) ≥ 2, 좌석 상한 이내 |
| 보상·전적 | `accountRecords`·보상은 roster만. 관전 구성원은 기록 없음 |
| 잠금(PR118-03) | `playing_users` 예약은 roster만 |
| 호환 | 구 클라이언트는 `ready`만 보내므로 항상 참가로 취급. 구 Worker는 `intent`를 모르므로 새 페이지는 `features.lobbyWatch` 플래그로만 노출 |

### `quick-match.spec.ts:42` 키보드 실패의 원인과 재현 조건

- **증상:** Space로 굴린 직후 ArrowDown을 눌러도 `tr.score-row-selected`(에이스)가 생기지 않는다.
- **원인:** 온라인 게임의 단축키는 `can = myTurn && !sending && !rolling && online`일 때만 동작한다(`src/play/OnlineGame.tsx`, `useGameShortcuts`). 굴림 결과(`.board-top b` = 1)는 서버 이벤트가 오면 바로 표시되지만, `can`은 명령 ack(`sending`)와 주사위 정착(`rolling`)이 끝난 뒤에 참이 된다. 그 사이에 누른 키는 무시되고, 차례가 다시 조작 가능해질 때 선택도 초기화된다(설계된 동작). 테스트는 이 구간에 키를 눌렀다.
- **재현 조건:** 굴림 표시와 `can` 복귀 사이에 키를 누르면 재현된다. 이 샌드박스(로컬 wrangler + 미리 설치된 Chromium)에서는 이 브랜치와 origin/main 모두에서 6회 중 5회 실패했다. 어느 기기가 선공인지(무작위 `flip`)와는 무관했다(휴대폰·데스크톱 선공 모두 실패, 휴대폰도 12행 점수판을 그림). 같은 구조인 `multi-online.spec.ts`의 3인 키보드 테스트도 병렬 2 worker에서 6회 중 3회 실패했다.
