# 온라인 소셜 · 계정 설계 (제품 Phase 3·4, 2026-11-24)

> **번호 주의:** 제품 로드맵 Phase 3(온라인 소셜)·Phase 4(계정·게스트)다. 온라인 서버 개발 기록의 "Online v0.1 Phase 1~4"(엔진·전송·Workers·배포)와 다르다.
> 제품 로드맵 순서: 1 모바일 UX·성능 → 2 게임 연출 → **3 온라인 소셜** → **4 계정·게스트** → 5 퀘스트·업적 → 6 재화·상점·꾸미기 → 7 AI 전략 복기 → 8 바이럴·경쟁 → 9 수익화 → 10 플랫폼 확장.

## 공통 원칙

- 서버 권한형 방(`OnlineRoom`, Durable Object 1개/방)을 그대로 쓰고, 프로토콜은 **추가만** 한다(`WIRE_VERSION` 1 유지). 구 클라이언트는 새 메시지를 무시하고, 새 클라이언트는 구 서버에서 새 버튼이 반응하지 않을 뿐 대전은 된다 → **Worker 먼저 배포, 그다음 Pages**.
- 소셜 데이터(채팅·이모티콘)는 **저장하지 않는다**. 행 쓰기는 경기 진행·재대결·관전 동의처럼 다시 접속해도 유지되어야 하는 상태에만 쓴다.

## 1. 재대결 (PR B)

### 방식 비교

| | 새 방 생성 | **기존 방 재사용 (채택)** |
|---|---|---|
| 요청 | 방 생성 API + 디렉터리 쓰기 + 새 DO + 두 사람 재입장·재연결 | 같은 소켓에서 메시지 1개씩 |
| 행 쓰기 | 디렉터리 2 + 새 방 레코드 3~4 | 방 레코드 1 (새 경기 시작) + 디렉터리 1 (일일 한도 계수) |
| 좌석 인증 | 새 토큰 발급·저장 | 기존 좌석 토큰 그대로 |
| 초대 링크 | 다시 공유 필요 | 불필요 |
| 상태 분리 | 자연스러움 | 경기마다 **새 무작위 matchId**와 새 이벤트 로그(이전 로그는 교체), 결과는 방 전적(`series`)에만 요약 |

### 동작
- 경기 종료 후 `{t:"rematch", op:"request"|"cancel"|"decline"}`. 요청 목록은 방 레코드에 저장(새로고침·재접속 후에도 유지). 모든 좌석이 요청하면 새 경기 시작.
- 동시 요청: 방은 메시지를 하나씩 처리하므로 두 번째 요청이 곧 수락이다. 같은 사람의 중복 요청은 쓰기 없이 무시.
- 새 경기: 새 matchId(`m_`+16자, 96비트), 좌석 순서를 한 칸 회전 → **2인은 선공이 매번 바뀜**. 점수·타이머·고정 순서·요청 상태 초기화, 이벤트 로그 새로 시작(감사·재구성 그대로 동작).
- 방을 나감(`bye`): 그 좌석 토큰 폐기, 상대에게 "상대가 방을 나갔어요"·재대결 불가. 모두 나가면 방 삭제.
- 제한: 방당 경기 20회, 플레이어당 저장되는 변경 1회/초, 경기당 40회, 방 수명(48시간) 2시간 전부터 새 경기 불가, **재대결도 일일 한도(DAILY_ROOM_LIMIT)에 포함**(이름은 방이지만 이제 "하루 경기 수"를 센다).
- 결과 화면: 승패·최종 점수, 방 전적(n승 m패), 재대결/수락/거절/취소, 새 방 만들기, 로비로.

- 원래 후보에 "잘 부탁해요!"(대국 시작 인사)를 더했다. 모두 긍정·중립 표현이라 조롱에 쓰기 어렵다.
- 전송 제한(연결별, 메모리·소켓 첨부 데이터 — 저장 없음): 연속 3개, 이후 2초에 1개(분당 약 30개), 같은 항목은 1.5초 안에 반복 불가. 클라이언트도 0.7초 동안 버튼을 잠가 거절 탭을 줄인다.
- 전달: 방의 모든 플레이어(본인 포함 — 화면 확인용 메아리)와 관전자에게 **실시간으로만**. 저장·재전송 없음 → 재접속·새로고침 시 과거 메시지가 다시 재생되지 않는다.
- 표시: 보낸 사람의 **점수 칩 안**에서 2.6초(이모티콘은 작은 튀어나옴, 문장은 페이드). 주사위·버튼·점수판을 가리지 않는다. "동작 줄이기"(시스템 설정)·"모션 간단히"(앱 설정)에서는 정지 표시.
- 상대 메시지 숨기기: 패널의 체크박스, 이 기기에 저장.
- 패널: 도구 줄의 "채팅" 버튼 → 휴대폰은 하단 시트, 넓은 화면은 팝오버. 관전자는 버튼이 없다.
- 게임 상태 독립: 채팅은 엔진 명령이 아니므로 버전·타이머·이벤트 로그에 영향이 없다(테스트로 확인).

### 확장 구조 (이번에 구현하지 않음)
각 항목에 `tier`("free"; 이후 shop·quest·achievement·limited), `acquisition`("default"; 이후 inventory 필요), `style`(말풍선 외형 "default"; 이후 silver·gold), `retired`(ID 재사용 금지 대신 은퇴)가 있다. 서버 검사 `canSend(id, owned)`는 "보유 목록"을 받으므로, 인벤토리가 생기면 `기본 ∪ 계정 인벤토리`를 넘기면 된다. 장착 목록(loadout)은 ID 배열, 최대 12개(`MAX_LOADOUT`).

## 3. 실시간 관전 (PR C)

### 권한 구조
- **관전은 기본 꺼짐.** 각 플레이어가 "관전 허용"을 켜고, **모든 좌석이 허용했을 때만** 관전 키가 유효하다. 관전 링크: `…/YachtLab/?watch=CODE&k=KEY#spectate`.
- 관전 키는 좌석 토큰과 **완전히 별개**인 읽기 전용 자격(무작위 18바이트). 좌석 토큰·플레이어 ID·명령 ID는 관전자에게 절대 전달되지 않는다.
- **누구든 끄면 즉시 철회:** 키 폐기 → 연결된 관전자 종료(코드 4003) → 옛 링크 거부. 다시 켜면 새 키(새 링크). 대기실에 새 플레이어가 앉으면(그 사람은 아직 동의 전) 관전 중단.
- 방 코드만으로는 관전할 수 없고, 관전 링크가 유출돼도 플레이어가 끄면 막힌다("비공개 방 정책 우회 불가").
- 관전자 소켓은 `hello` 대신 `watch`로 시작하고 `viewFor(state, null)`(중립 시점: `you`·`legal` 없음, 다른 사람 명령 ID 제거)을 받는다. 굴림·고정·점수·시작·기권·재대결·채팅·관전 설정·좌석 인증(`hello`) 등 **모든 조작 메시지는 거부**(`SPECTATOR`).
- 관전자가 보는 것: 두 플레이어 점수 칩·주사위 값·굴림·공유 고정 순서·점수판·턴·남은 시간·결과, 플레이어의 프리셋 채팅·이모티콘(관전자는 보낼 수 없음). 재대결이 시작되면 이어서 관전.

### 비용·남용 제한 (Workers Free 기준, 보수적)
- **방당 관전자 최대 5명**, 방 소켓 최대 14개(플레이어 탭 여유 + 관전자). 근거: 관전자는 송신만 받는다 — Durable Object에서 **송신 메시지는 요청으로 세지 않고**, 관전자의 수신 메시지는 접속 시 1개뿐이며 keep-alive 핑은 자동 응답(깨우지 않음)이다. 비용은 브로드캐스트 직렬화 CPU(duration)인데, 한 경기 약 130 이벤트 × 관전자 5명이면 수 ms 수준이다. 그래도 공유 계정의 무료 한도를 고려해 작게 시작하고, 대시보드 지표를 본 뒤 늘린다.
- 관전 연결도 기존 방당 분당 연결 20회, IP 해시별 조회 속도 제한(디렉터리, 메모리 계수)을 그대로 거친다.
- **관전은 저장 쓰기 0회**(관전자 수는 메모리, 관전자 표시·키는 소켓 첨부 데이터 — Hibernation 후에도 유지, 깨어날 때 키를 다시 검사). 관전 기록은 영구 저장하지 않는다. 관전 허용을 켤 때만 행 쓰기 1회(켜기는 플레이어당 1초 1회로 제한, **끄기는 제한 없음** — 개인정보 보호 동작).
- 방이 정리되면 모든 관전 소켓도 닫힌다.
