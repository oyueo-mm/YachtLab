# 온라인 소셜 · 계정 설계 (제품 Phase 3·4, 2026-11-24)

> **번호 주의:** 제품 로드맵 Phase 3(온라인 소셜)·Phase 4(계정·게스트)다. 온라인 서버 개발 기록의 "Online v0.1 Phase 1~4"(엔진·전송·Workers·배포)와 다르다.
> 제품 로드맵 순서: 1 모바일 UX·성능 → 2 게임 연출 → **3 온라인 소셜** → **4 계정·게스트** → 5 퀘스트·업적 → 6 재화·상점·꾸미기 → 7 AI 전략 복기 → 8 바이럴·경쟁 → 9 수익화 → 10 플랫폼 확장.

## 공통 원칙

- 서버 권한형 방(`OnlineRoom`, Durable Object 1개/방)을 그대로 쓰고, 프로토콜은 **추가만** 한다(`WIRE_VERSION` 1 유지). 구 클라이언트는 새 메시지를 무시하고, 새 클라이언트는 구 서버에서 새 버튼이 반응하지 않을 뿐 대전은 된다 → **Worker 먼저 배포, 그다음 Pages**.
- 소셜 데이터(채팅·이모티콘)는 **저장하지 않는다**. 행 쓰기는 경기 진행·재대결·관전 동의처럼 다시 접속해도 유지되어야 하는 상태에만 쓴다.

## 1. 재대결 (PR B)

### 방식 비교

| | 새 방 생성 | **기존 방 재사용 (채택)** |
|---|---|---|
| 요청 | 방 생성 API + 디렉터리 쓰기 + 새 DO + 두 사람 재입장·재연결 | 같은 소켓에서 메시지 1개씩 |
| 행 쓰기 | 디렉터리 2 + 새 방 레코드 3~4 | 방 레코드 1 (새 경기 시작) + 디렉터리 1 (일일 한도 계수) |
| 좌석 인증 | 새 토큰 발급·저장 | 기존 좌석 토큰 그대로 |
| 초대 링크 | 다시 공유 필요 | 불필요 |
| 상태 분리 | 자연스러움 | 경기마다 **새 무작위 matchId**와 새 이벤트 로그(이전 로그는 교체), 결과는 방 전적(`series`)에만 요약 |

### 동작
- 경기 종료 후 `{t:"rematch", op:"request"|"cancel"|"decline"}`. 요청 목록은 방 레코드에 저장(새로고침·재접속 후에도 유지). 모든 좌석이 요청하면 새 경기 시작.
- 동시 요청: 방은 메시지를 하나씩 처리하므로 두 번째 요청이 곧 수락이다. 같은 사람의 중복 요청은 쓰기 없이 무시.
- 새 경기: 새 matchId(`m_`+16자, 96비트), 좌석 순서를 한 칸 회전 → **2인은 선공이 매번 바뀜**. 점수·타이머·고정 순서·요청 상태 초기화, 이벤트 로그 새로 시작(감사·재구성 그대로 동작).
- 방을 나감(`bye`): 그 좌석 토큰 폐기, 상대에게 "상대가 방을 나갔어요"·재대결 불가. 모두 나가면 방 삭제.
- 제한: 방당 경기 20회, 플레이어당 저장되는 변경 1회/초, 경기당 40회, 방 수명(48시간) 2시간 전부터 새 경기 불가, **재대결도 일일 한도(DAILY_ROOM_LIMIT)에 포함**(이름은 방이지만 이제 "하루 경기 수"를 센다).
- 결과 화면: 승패·최종 점수, 방 전적(n승 m패), 재대결/수락/거절/취소, 새 방 만들기, 로비로.

각 항목에 `tier`("free"; 이후 shop·quest·achievement·limited), `acquisition`("default"; 이후 inventory 필요), `style`(말풍선 외형 "default"; 이후 silver·gold), `retired`(ID 재사용 금지 대신 은퇴)가 있다. 서버 검사 `canSend(id, owned)`는 "보유 목록"을 받으므로, 인벤토리가 생기면 `기본 ∪ 계정 인벤토리`를 넘기면 된다. 장착 목록(loadout)은 ID 배열, 최대 12개(`MAX_LOADOUT`).

## 3. 실시간 관전 (PR C)

### 권한 구조
- **관전은 기본 꺼짐.** 각 플레이어가 "관전 허용"을 켜고, **모든 좌석이 허용했을 때만** 관전 키가 유효하다. 관전 링크: `…/YachtLab/?watch=CODE&k=KEY#spectate`.
- 관전 키는 좌석 토큰과 **완전히 별개**인 읽기 전용 자격(무작위 18바이트). 좌석 토큰·플레이어 ID·명령 ID는 관전자에게 절대 전달되지 않는다.
- **누구든 끄면 즉시 철회:** 키 폐기 → 연결된 관전자 종료(코드 4003) → 옛 링크 거부. 다시 켜면 새 키(새 링크). 대기실에 새 플레이어가 앉으면(그 사람은 아직 동의 전) 관전 중단.
- 방 코드만으로는 관전할 수 없고, 관전 링크가 유출돼도 플레이어가 끄면 막힌다("비공개 방 정책 우회 불가").
- 관전자 소켓은 `hello` 대신 `watch`로 시작하고 `viewFor(state, null)`(중립 시점: `you`·`legal` 없음, 다른 사람 명령 ID 제거)을 받는다. 굴림·고정·점수·시작·기권·재대결·채팅·관전 설정·좌석 인증(`hello`) 등 **모든 조작 메시지는 거부**(`SPECTATOR`).
- 관전자가 보는 것: 두 플레이어 점수 칩·주사위 값·굴림·공유 고정 순서·점수판·턴·남은 시간·결과, 플레이어의 프리셋 채팅·이모티콘(관전자는 보낼 수 없음). 재대결이 시작되면 이어서 관전.

### 비용·남용 제한 (Workers Free 기준, 보수적)
- **방당 관전자 최대 5명**, 방 소켓 최대 14개(플레이어 탭 여유 + 관전자). 근거: 관전자는 송신만 받는다 — Durable Object에서 **송신 메시지는 요청으로 세지 않고**, 관전자의 수신 메시지는 접속 시 1개뿐이며 keep-alive 핑은 자동 응답(깨우지 않음)이다. 비용은 브로드캐스트 직렬화 CPU(duration)인데, 한 경기 약 130 이벤트 × 관전자 5명이면 수 ms 수준이다. 그래도 공유 계정의 무료 한도를 고려해 작게 시작하고, 대시보드 지표를 본 뒤 늘린다.
- 관전 연결도 기존 방당 분당 연결 20회, IP 해시별 조회 속도 제한(디렉터리, 메모리 계수)을 그대로 거친다.
- **관전은 저장 쓰기 0회**(관전자 수는 메모리, 관전자 표시·키는 소켓 첨부 데이터 — Hibernation 후에도 유지, 깨어날 때 키를 다시 검사). 관전 기록은 영구 저장하지 않는다. 관전 허용을 켤 때만 행 쓰기 1회(켜기는 플레이어당 1초 1회로 제한, **끄기는 제한 없음** — 개인정보 보호 동작).
- 방이 정리되면 모든 관전 소켓도 닫힌다.

## 4. 계정·게스트 (PR D)

### 4-1. 핵심 원칙
- **가입 강제 없음.** 닉네임만으로 AI·오프라인·온라인 대전, 초대 링크 입장, 채팅·재대결·관전 모두 가능. 로그인 팝업이나 가입 화면을 게임 시작·입장 경로에 넣지 않았다(홈의 "내 프로필 · 전적"에서만 선택).
- 사용자는 ID로 구분하고 닉네임은 표시용 라벨일 뿐이다(같은 닉네임 허용).
- 자격 증명 세 가지는 목적이 다르고 섞이지 않는다:

| 자격 | 범위 | 저장 위치 | 서버 저장 |
|---|---|---|---|
| 좌석 토큰 | 한 방의 한 좌석 | 브라우저 localStorage | SHA-256 해시 |
| 게스트 키 | 이 기기의 게스트 기록 | 브라우저 localStorage | 연결 시 guestId(키의 해시)만 |
| 계정 세션 | 로그인 | 브라우저 localStorage | SHA-256 해시, 30일, 계정당 20개, 만료 행 자동 정리(C4.2) |
| 관전 키 | 한 방의 읽기 전용 관전 | 링크 | 방 레코드(철회 시 폐기) |

### 4-2. 인증 아키텍처 비교 (Google 우선)

| 방식 | 보안 | 무료 범위 | Workers·DO 호환 | Pages 정적 호환 | 모바일·서드파티 쿠키 | 유지보수 | 판단 |
|---|---|---|---|---|---|---|---|
| **A. Worker가 OIDC 코드 흐름(PKCE+state+nonce, 비밀키 서버 보관) + 일회용 코드 → 베어러 세션 (채택)** | 높음(비밀키·토큰 검증 서버) | Workers Free 안 | 그대로 | 그대로 | 쿠키 불필요(로그인 중 10분 1st-party 쿠키만) | 중 | ✅ |
| B. 브라우저 Google Identity Services(One Tap) ID 토큰 → Worker 검증 | 중(공개 클라이언트, 토큰이 페이지 JS에 노출) | 무료 | 호환 | 호환 | One Tap이 ITP·인앱에서 불안정 | 낮음 | 보류 |
| C. Cloudflare Access / 외부 IdP(Auth0·Firebase 등) | 높음 | 무료 범위·한도 별도, 새 계정·서비스 필요 | 간접 | 호환 | 다양 | 외부 의존 | 불채택(새 외부 리소스·승인 필요) |
| D. 자체 비밀번호 | 직접 구현 위험 | — | — | — | — | 높음 | 금지(요구사항) |
| E. 쿠키 세션(SameSite=None) | 높음 | — | — | github.io ↔ workers.dev는 **서로 다른 사이트** | iOS Safari·인앱에서 서드파티 쿠키 차단 | — | 불채택 |

- **흐름:** Pages에서 "Google로 로그인" → `workers.dev/auth/google/start?cs=SHA256(탭 비밀값)` → Google(scope `openid`만, `prompt=select_account`) → `workers.dev/auth/google/callback` → 코드 교환(client_secret+PKCE verifier) → **ID 토큰 검증(RS256·JWKS·iss·aud·exp·iat·nonce)** → 계정 생성/조회 → `Pages#login=<userId>.<일회용 코드>`로 복귀 → 페이지가 탭 비밀값과 함께 교환 → 세션(베어러 토큰).
- **보호:** state(CSRF), nonce(재생), PKCE S256(코드 가로채기), state·nonce·verifier는 AES-GCM으로 봉인한 HttpOnly·Secure·SameSite=Lax·`__Host-` 쿠키(10분), 일회용 코드는 2분·1회·**시작한 탭의 비밀값에 묶임**(공격자가 자기 코드를 피해자에게 심는 로그인 CSRF 방지), 콜백은 `Referrer-Policy: no-referrer`, 코드는 URL 조각(#, 서버로 전송 안 됨)으로 받고 즉시 주소창에서 지움. 세션은 로그인 때마다 새로 발급(세션 고정 불가). 반환 주소는 설정값(APP_URL) 고정 — 열린 리디렉션 없음. 허용 Origin 외 API 쓰기 403. 로그에는 오류 종류만 남기고 토큰·클레임을 남기지 않는다.
- **계정 ID:** `u_` + SHA-256("yachtlab-user:google:"+sub) 앞 22자. Google의 sub·이메일은 저장·반환하지 않는다. 카카오·Apple을 추가하면 공급자별로 다른 ID가 생기며, 한 계정에 여러 공급자를 연결하려면 그때 연결 테이블을 추가한다(문서화만).
- **인앱 브라우저:** Google은 카카오톡 등 임베디드 웹뷰의 OAuth를 차단한다(`disallowed_useragent`). 프로필에서 인앱 브라우저를 감지해 "외부 브라우저로 열기"를 안내한다. 게임·초대·관전은 인앱에서도 그대로 동작.
- **기능 플래그:** `GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET`·`AUTH_SECRET`(32자 이상) 시크릿과 `APP_URL`이 모두 있어야 켜진다. 없으면 `/api/auth/config`가 `{google:false}`, 로그인 경로는 404, 프로필은 "회원 로그인은 준비 중이에요". **가짜 성공 처리 없음.**
- **테스트와 운영 구분:** 자동 테스트는 로컬에서 만든 RSA 키의 **가짜 OIDC 제공자**로 검증 로직만 확인한다(`tests/accounts.test.ts`). 운영 코드에는 테스트 전용 로그인 경로가 없다. **실제 Google 로그인은 시크릿 설정 후 사람이 직접 확인해야 하며, 이번 작업에서는 수행하지 못했다.**

### 4-3. 저장소 비교

| | 기존 방 DO에 저장 | **사용자별 SQLite DO (채택)** | Cloudflare D1 | 외부 DB |
|---|---|---|---|---|
| 보안 | 방 데이터와 섞임 | 인증된 userId의 객체에만 도달 — 격리가 구조적 | 쿼리마다 userId 조건 필요 | 별도 자격 |
| 비용(무료) | 행 쓰기 공유 | 같은 DO SQLite 무료 한도(행 쓰기 10만/일 계정 공유) | 별도 무료 한도이나 **새 리소스 생성 필요** | 별도 계정 |
| 조회 | 불가 | 한 사용자 조회 빠름 | 사용자 간 쿼리(랭킹) 가능 | 가능 |
| 동시성 | — | 사용자별 직렬 실행(중복 삽입·경합 없음) | 트랜잭션 | — |
| 확장성 | — | 사용자 수에 선형 | 단일 DB 10GB(무료 500MB) | — |
| 백업 | 방은 48시간 후 삭제 | SQLite DO의 Point-in-Time Recovery(공식 문서상 30일, 운영 절차 미구현) | Time Travel | 외부 |
| 운영 | — | 같은 Worker 배포(마이그레이션 v2로 클래스 추가) | 생성·바인딩·마이그레이션 | 높음 |

- 채택: `UserStore`(계정당 1개) + `GuestLink`(게스트 ID당 1개, 첫 연결 계정 기록). 새 클라우드 리소스·결제 없이 기존 Worker 배포만 필요. 랭킹처럼 사용자 간 집계가 필요해지면 그때 D1(별도 승인)을 검토.
- 테이블(UserStore): `user`(1행: user_id, provider, nickname, created_at), `sessions`(해시·만료), `login_codes`(해시·탭 해시·만료), `matches`(record_id PK, 종료 시각, 모드, 출처, 검증 수준, 결과, 점수, JSON), `guests`(연결한 guestId).

### 4-4. 게스트
- 기기별 게스트 키(32바이트) → guestId = `g_`+SHA-256 앞 22자. 닉네임은 기존 온라인 닉네임(`yachtlab.online.name`)과 공유.
- 기기 기록: AI 대전 종료 시, 온라인 경기 종료 시(내 화면의 사본) `localStorage`에 최근 500개. 브라우저 데이터를 지우면 사라진다는 점을 프로필에 표시.
- 새로고침·재접속 복구는 기존 좌석 토큰 구조 그대로.

### 4-5. 닉네임 정책 (`src/identity/nickname.ts`, 서버·브라우저 공용)
- NFC, 앞뒤 공백 제거, 연속 공백 1칸. **사용자 인식 문자(grapheme) 1~12자**(한글 음절·결합 이모지 1자), **UTF-8 48바이트 이하**.
- 거부: 제어·형식(제로폭·양방향 재정의)·사설·서로게이트 문자, 줄/문단 구분자, `< > " \` \\`, 결합 문자 3개 초과(자르고), 이모지 밖의 ZWJ.
- 사칭 방지: NFKC·소문자·기호 제거 "골격"이 운영자·관리자·admin·moderator·yachtlab·요트랩·공식·official·staff·개발자·system·고객센터·support 등을 포함하거나 gm·mod·운영·관리·dev·root와 같으면 거부.
- 부적절 닉네임: 짧은 욕설 목록만 기본 차단(완전한 필터 아님). 신고·운영 도구는 범위 밖.
- 표시: 점수 칩·말풍선·프로필은 말줄임. 온라인 방 입장도 같은 정책(구 기록은 엔진의 24자 검사로 그대로 재생).
- 확장(미구현): 색·효과·칭호·변경권은 닉네임과 별도 프로필 필드로 추가한다. 이번엔 기본 설정·변경만(회원 하루 10회).

### 4-6. 경기 기록과 신뢰 수준 (`src/identity/records.ts`)

| 출처 | 검증 수준 | 누가 쓰나 | 공개 프로필·향후 보상에 사용 |
|---|---|---|---|
| `server` | `server-verified` | 온라인 방이 자기 엔진 상태로 직접 작성 | ✅ |
| `device` | `client-reported` | 회원 기기의 AI·오프라인 기록 업로드 | ❌ |
| `guest-import` | `client-reported` | 게스트 기록을 계정에 연결 | ❌ (승격 금지) |

- 기록 필드: recordId(온라인=matchId, 기기=`d_`+무작위), 모드, 규칙 ID(`yacht12@1`), 출처·검증 수준, 시작·종료 시각, 이름, 점수판(족보별 결과), 총점, 승/패/무, 종료 사유(완료·기권·시간 초과), 상대(이름·종류·계정 ID·점수), AI 난이도.
- **서버 공식 결과 저장:** 방이 경기 종료 이벤트와 **같은 쓰기**로 회원 좌석마다 결과를 아웃박스에 넣고, 저장 직후 계정 DO에 전달한다. 계정 DO는 matchId 기본키로 **중복을 무시**하므로 재시도·재접속·서버 재시작·응답 유실로 두 번 세지 않는다. 전달 실패는 방 알람으로 1분 뒤 재시도, 객체가 깨어날 때도 재시도, 방 삭제 직전 마지막 시도. 재대결은 새 matchId → 새 기록.
- 업로드 기록은 서버가 다시 검사(카테고리·점수 범위·**점수판 합계 = 총점**·시각)하고 출처를 무조건 `client-reported`로 낮춘다. 기기가 상대 계정 ID를 주장해도 지운다.
- 상세 리플레이·전체 굴림은 저장하지 않는다(결과·점수판만).

### 4-7. 게스트 기록의 계정 이전
- 로그인 후 프로필의 "이 기기 기록 n개 계정에 연결"(사용자가 명시적으로 누를 때만).
- 서버는 게스트 키로 guestId를 계산하고 `GuestLink`에 **첫 연결 계정**을 기록 → 다른 계정은 같은 게스트를 연결할 수 없음(409). 같은 계정의 재시도·다른 기기는 허용.
- 기록 ID 단위로 중복 무시(재시도·두 번 누름 안전), 150개씩 나눠 전송, 하루 1000개·계정 5000개 한도.
- 이전된 기록은 `guest-import`/`client-reported` 그대로 — 공식 온라인 전적으로 승격하지 않는다. 코인·퀘스트 보상 이전 정책은 경제 단계에서 결정.

### 4-8. 프로필·통계
- 기본: 닉네임(수정), 기본 아이콘(첫 글자), 게스트/회원, 처음 플레이·가입일, 경기 수, 승·패·무, 승률(무승부 0.5), 최고·평균 점수, 요트·라지 스트레이트 횟수, 최근 10경기(서버 확인/기기 기록 표시).
- 상세(접힘): 최근 점수 추이(선 1개), 모드별 경기 수, AI 난이도별 전적, 온라인 상대별 전적(계정은 ID, 게스트는 이름 기준), 족보별 평균·달성 횟수.
- 전체/온라인/AI 필터. 기록이 없으면 "아직 기록이 없어요"(가짜 수치 없음).
- 공개 프로필(다른 사람에게 보이는 것): 닉네임, 가입 **월**, 서버 검증 온라인 경기 수·승패·최고·평균만. 이메일 등 개인정보 없음(애초에 수집 안 함). 온라인 결과 화면에서 상대가 회원이면 "상대 프로필".
- 레이팅·랭킹은 계산하지 않는다(서버 검증 기록만 입력으로 쓰도록 구조만 준비).

### 4-9. 개인정보·삭제·보존
- 수집: 내부 계정 ID, 공급자 이름, 닉네임, 시각, 세션·코드 해시, 경기 결과. **수집 안 함:** 이메일·이름·사진·Google 토큰·IP 원문(속도 제한은 IP 해시를 메모리에만).
- 보존: 세션 30일(만료 행은 로그인·인증·계정 알람에서 삭제, 계정당 20개), 로그인 코드 2분, 경기 기록·게스트 연결은 계정 삭제 시까지, 방 데이터 최대 48시간(기존). 탈퇴 후: 삭제 시각·폐기 친구 코드 30일, 정리 대기열(완료 시 삭제), 차단한 사람의 목록에 가명 내부 ID(C4.2, D-C42-1·2).
- 사용자 통제: 로그아웃, 모든 기기 로그아웃, 닉네임 수정, **계정 삭제**(확인 후 계정 DO 전체 삭제 + 게스트 연결 해제). 진행 중인 방(최대 48시간)에 남은 계정 ID는 방과 함께 자동 삭제.
- 접근 권한: `/api/me*`는 세션의 userId 객체에만 접근(경로에서 다른 ID를 받지 않음). 공개 프로필은 공개 필드만.

### 4-10. 향후 확장을 위한 공통 구조 (구현은 최소)
- 사용자 ID `u_…`, 게스트 ID `g_…`, 경기 ID `m_…`, 기기 기록 ID `d_…`, 프리셋/이모티콘 ID `chat.*`/`emote.*` — 모두 불변.
- 경기 종료 이벤트 타입 `MatchFinishedEvent {eventId, type:"match.finished", userId, record}` 정의. 퀘스트·코인·업적은 **(eventId = matchId+userId) 기본키 테이블**에 처리 결과를 기록해 멱등 처리하고, `verification === "server-verified"`만 보상 입력으로 쓴다(문서화, 테이블 미생성).
- 이번에 만들지 않은 것: 인벤토리·재화·퀘스트·업적·랭킹 테이블.

### 4-11. 검증 (PR D)

## 5. Cloudflare 비용·한도 (Workers Free, 다른 Worker와 계정 한도 공유)

공식 무료 한도(PR #44 시점 공식 문서 확인값, D-021): Workers 요청 10만/일, DO 요청 10만/일(**수신 WebSocket 메시지 20:1 환산, 송신 무료**), DO duration 13,000 GB-s/일, SQLite 행 읽기 500만/일·**행 쓰기 10만/일**·저장 5GB. 초과 시 과금이 아니라 실패(Free). 이 계정은 `ideadock-auth`와 한도를 공유한다.

| 기록 가져오기 | 기록당 ≈2~3 | — | 하루 1000개/계정 |

- **추가 비용 가능성:** Free 플랜에서는 한도를 넘으면 실패할 뿐 과금되지 않는다. 다만 계정이 Paid로 바뀌면 초과 과금 대상이 되므로 기존 원칙(배포 워크플로의 무료 플랜 확인)을 유지한다. "비용이 절대 없다"고 보장하지 않는다.
- 유지되는 보호 장치: 하루 방(=경기) 300, 동시 방 50, 분당 생성 5·입장 30, Origin 검증, 요청 크기 제한(방 1KB, 가져오기 160KB), 소켓 토큰 버킷, 방당 연결 분당 20, 보존 기간 정리. 새로: 채팅 속도, 관전자 5, 재대결 쿨다운·횟수, 로그인·교환·프로필 속도 제한(메모리, 쓰기 0), 닉네임 변경 하루 10회, 가져오기 한도.
- 공유 계정 위험: 분산된 남용은 IP 해시 제한으로 막기 어렵다 → Cloudflare 대시보드 사용량을 보고 `DAILY_ROOM_LIMIT` 조정, 필요 시 WAF 속도 제한(무료 범위는 대시보드에서 확인).

## 6. 사용자가 직접 해야 하는 설정 (Google 로그인 켜기)

1. **Google Cloud Console** → Google Auth Platform(또는 APIs & Services → OAuth consent screen)
   - 앱 이름 `YachtLab`, 지원 이메일, User type **External**.
   - 범위: `openid`만(민감 범위 아님 → 앱 검증 불필요). 게시 상태가 **Testing**이면 등록한 테스트 사용자만 로그인 가능 → 모두에게 열려면 **Publish app**.
2. Credentials → **Create credentials → OAuth client ID → Web application**
   - **Authorized redirect URI:** `https://yachtlab-online.hoho96385210.workers.dev/auth/google/callback` (정확히 일치해야 함)
   - Authorized JavaScript origins는 필요 없음(서버 측 흐름).
   - 발급된 Client ID와 Client secret을 복사.
3. **Cloudflare 대시보드** → Workers & Pages → `yachtlab-online` → Settings → **Variables and Secrets** → Add → Type **Secret**
   - `GOOGLE_CLIENT_ID` = 2의 Client ID
   - `GOOGLE_CLIENT_SECRET` = 2의 Client secret
   - `AUTH_SECRET` = 무작위 48자 이상(예: 터미널 `openssl rand -base64 48`)
   - 시크릿은 저장소·GitHub·프런트엔드 번들에 넣지 않는다. `APP_URL`은 `worker/wrangler.toml`에 이미 있음(`https://oyueo-mm.github.io/YachtLab/`).
4. 확인: `https://yachtlab-online.hoho96385210.workers.dev/api/auth/config`가 `{"google":true}` → 공개 사이트 홈 → 내 프로필 → "Google로 로그인" → 로그인 후 "회원" 표시 → 다른 기기에서 같은 계정 로그인 → 같은 기록.
5. 끄기: 위 시크릿 중 하나를 삭제하면 즉시 로그인 기능이 꺼진다(게스트 기능은 그대로).
