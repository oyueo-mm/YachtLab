# 빠른 대전·공개 관전방·PC 온라인 도구 줄 (제품 Phase 4.5, 2026-11-24)

> 최신 전역 큐, D-045 공개 빠른 대전, 친구 대전 권한 및 A6 계약은 [C3 전역 매칭과 관전](./C3-BACKGROUND-MATCH.md)을 참조한다. 아래 내용은 제품 Phase 4.5 시점의 기록이다.

> 결정 기록: DECISIONS D-038. 이전 계획: [MATCHMAKING-SPECTATE-PLAN](./MATCHMAKING-SPECTATE-PLAN.md)(계획 → 이 문서가 구현).

## 1. 온라인 메뉴

온라인 대전 화면은 **빠른 대전 · 친구 대전 · 관전방** 3개 탭이다. 서버가 `/api/features`로 빠른 대전을 지원한다고 답할 때만 탭을 보이고, 그렇지 않은 서버(구버전 Worker·로컬 Node 개발 서버)는 친구 대전만 보인다. 마지막으로 연 탭은 기기에 기억한다. 초대 링크(`?room=`)는 지금처럼 해당 방 입장 화면으로 바로 간다.

## 2. 빠른 대전(무작위 매칭)

| 항목 | 구현 |
|---|---|
| 위치 | 전역 Durable Object `MatchHub`(마이그레이션 v3, 같은 Worker, Workers Free SQLite DO). 새 유료 리소스 없음 |
| 대기 | 대기자 1명 = Hibernation WebSocket 1개(`/ws/match`). 대기 정보는 **소켓 첨부 데이터**에만 → 기다리는 동안 저장소 쓰기 0, 객체 퇴출 후에도 유지 |
| 게스트·회원 | 둘 다 가능. 회원은 세션을 첫 메시지로 보내고 허브가 `UserStore.authenticate`로 확인 |
| 원자적 배정 | 두 대기자를 고르고 `pairing`으로 표시하는 구간에 `await`가 없음 → 동시 요청에서도 한 사람이 두 경기에 배정되지 않음(테스트: 7명 동시 → 3경기, 좌석 중복 0) |
| 자기 자신 | 같은 티켓(탭)·같은 계정·같은 기기 ID(브라우저)끼리는 매칭 안 함. **같은 IP는 막지 않음**(공용 와이파이·통신사 NAT) |
| 반복 상대 | 같은 두 사람은 10분 안에 다시 짝짓지 않음. 단 둘 다 20초 이상 기다렸으면 허용(둘만 접속한 경우 대비). 보상 측 상한(같은 회원 상대 하루 3경기 보상)은 경제 PR에서 |
| 중복·진행 중 | 같은 계정이 다른 화면에서 이미 대기 중이면 거부. 진행 중인 무작위 대전이 있으면 `IN_MATCH`와 방 코드를 돌려주고 화면은 "진행 중인 경기로 돌아가기" 제공 |
| 새로고침·끊김 | 티켓은 탭의 sessionStorage. 새로고침하면 같은 티켓으로 대기를 이어 가고(새 소켓이 옛 소켓을 대체, 대기 순서 유지), 매칭 직후 끊겨도 결과(방 코드+좌석 토큰)를 티켓 해시로 5분간 보관해 같은 좌석을 다시 받음 |
| 유령 대기열 | 15초마다 `alive`, 45초 무응답이면 제거. 최대 대기 5분 후 만료 안내 |
| 경기 생성 | `RoomDirectory.allocateFor("random")` → `YachtRoom.createMatched`: 두 좌석 입장 + 시작을 **저장 1회**로 기록. 선공은 서버가 무작위. 초대 코드로 끼어들기 불가 |
| 상대 없음 | 20초 뒤 "계속 기다리기 / AI와 대전하기" 안내. AI는 항상 AI로 표시(사람인 척하지 않음) |
| 한도 | 빠른 대전도 `DAILY_ROOM_LIMIT`(300)에 포함, 한도의 95%부터 빠른 대전 생성을 멈춰 진행 중 경기·재대결 몫을 남김. `MAX_ROOMS` 50 유지. `/ws/match` 연결은 IP 해시당 분당 30회 |
| 랭크·레이팅 | 이번 범위 제외 |

## 3. 공개 관전방

- 빠른 대전 시작 전에 **"내 경기를 관전방에 공개"**(기본 꺼짐, 기기에 기억)를 묻는다. **두 사람 모두 허용한 경기만** 관전이 켜진 채 시작되고 공개 목록에 오른다.
- 목록 항목: 두 플레이어 닉네임, 프로필 아이콘·닉네임 효과(서버가 검증한 장착 정보), 현재 점수, 라운드, 관전자 수, 관전하기 버튼. 좌석 토큰·관전 키·계정 ID는 목록에 없다(테스트로 확인).
- 목록은 허브 메모리(손실 허용 캐시). 방이 라운드·점수·관전자 수가 바뀔 때만 갱신을 보내고(경기당 약 25회 DO 요청, 행 쓰기 0), 경기 종료·동의 철회·방 정리 때 즉시 삭제, 3분간 갱신이 없으면 만료.
- 조회 `GET /api/spectate/rooms`: `cache-control: public, max-age=5`, IP 해시당 분당 30회. 화면은 탭이 보일 때만 10초마다 갱신. 실시간 연결은 **관전하기를 누를 때만** 연다(`POST /api/spectate/:code/watch` → 관전 키 → 기존 관전 화면).
- 철회: 누구든 관전을 끄면 기존 규칙대로 키 폐기·관전자 즉시 연결 해제·목록 삭제. 방당 관전자 5명, 관전자 조작·메시지 불가 그대로.
- 친구 대전의 비공개 관전 링크는 변경 없음.

## 4. PC에서 채팅·이모티콘·관전 버튼이 보이지 않던 문제

재조사 결과(2026-11-24): main 코드에서는 1920·1366·1024·800px 폭 모두 버튼이 화면 안에 보였다(새 Playwright 테스트 `tests/ui/quick-match.spec.ts`가 폭별 위치를 측정). 원인 후보와 조치:

| 후보 | 확인 | 조치 |
|---|---|---|
| 브라우저가 **이전 배포 번들**(PR B #51 이전, 채팅·관전 버튼 자체가 없음)을 캐시 | GitHub Pages HTML은 최대 10분 캐시, 탭을 오래 열어 두면 계속 구버전 | **빌드 ID 확인 추가**: 빌드마다 `version.json`을 만들고, 온라인 화면·홈에서 캐시 없이 비교해 다르면 "새 버전이 나왔어요 · 새로고침" 배너 |
| 서버가 관전 상태를 보내기 전(연결 중·구버전 서버) `SpectateControl`이 **아무것도 그리지 않음** | 코드 확인(`if (!state) return null`) | 상태가 없어도 비활성 버튼으로 항상 표시 |
| 오프라인 AI·로컬 대전 화면 | 설계상 없음 | 변경 없음 |

도구 줄 재배치(PC): `방 코드 | [장착 이모티콘 바로 보내기 버튼 + 채팅·이모티콘 패널] | 관전 설정 · 기권`. 채팅·이모티콘은 보드 바로 위에서 한 번에 누를 수 있고, 관전 설정과 기권은 구분선으로 분리했다. 휴대폰(≤760px)은 기존 한 줄 배치를 그대로 유지(이모티콘 바는 숨기고 패널에서 선택).
