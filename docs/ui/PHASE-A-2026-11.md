## 1. 첫 굴림 최악 프레임 — 원인 재검증

이전 보고(PR #49)는 "물리 사전 계산 미완료 + 높은 초기 해상도"를 원인으로 추정했다. 코드와 측정으로 다시 확인한 결과는 다르다.

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 물리 사전 계산 미완료 | 진단 기록 `prepared`, `simMs` | **아님.** 첫 굴림 8/8회 모두 사전 계산 재사용(sim 3~4 ms). |
| 2배 초기 해상도 | 성능 우선(1.5배)으로 같은 측정 | **아님.** 1.5배에서도 첫 프레임 뒤 긴 작업 ~60 ms 그대로. |
| 효과음(AudioContext 생성) | 음소거로 같은 측정 | **아님.** 동일. |
| GPU 첫 그리기(셰이더 링크·텍스처 준비) | Chrome 트레이스(`Tracing`) | **원인.** 첫 프레임 직후 `Commit → GLES2::ReadPixels → WaitForCmd` 47 ms 동안 메인 스레드가 GPU 프로세스의 첫 WebGL 작업(46 ms)을 기다림. |

- 기존 `warmUp()`은 주사위를 화면 밖(y = −40)에 두고 `compile()`+`render()`를 했다. 화면 밖이라 **실제 그리기가 일어나지 않았고**, 드라이버의 셰이더 링크·텍스처 준비가 첫 굴림 프레임으로 밀렸다(접촉 그림자 셰이더는 컴파일조차 안 됨).
- `ReadPixels` 대기 자체는 헤드리스 소프트웨어 합성(SwiftShader)의 특성이라 실기기와 다르다. 하지만 "첫 실제 그리기에서 드라이버가 셰이더를 링크"하는 비용은 모바일 GPU(Adreno·Mali·Apple)에서도 알려진 현상이라 같은 대응이 유효할 것으로 본다(실기기 미검증).

### 같은 턴 재굴림의 숨은 문제
측정 중 **빠른 재굴림(굴림 직후 바로 다시 굴림)은 사전 계산이 0/8회** 재사용되어 탭마다 메인 스레드에서 물리 40~50 ms(CPU 4배)를 돌린다는 것을 발견했다. 주사위가 멈춘 뒤 다음 던지기 준비를 `MOVE_MS+60 = 320 ms` 기다린 다음 유휴 시간에만 시작했기 때문이다.

## 2. 검토한 방법과 채택 여부

| 방법 | 판단 | 근거 |
|---|---|---|
| 첫 진입 시 물리 사전 준비 | 이미 구현됨(유지) | 첫 굴림 8/8 재사용 |
| 셰이더·텍스처 사전 준비 | **채택(개선)** | 보이는 위치에 한 번 실제 그리기 → 같은 태스크에서 `clear()` (화면에 아무것도 안 나타남), `initTexture()`로 밉맵까지 업로드 |
| 유휴 시간 활용 | **채택** | 위 준비를 레이아웃 직후가 아니라 `requestIdleCallback`(최대 600 ms)에서 실행 → 게임 진입을 막지 않음. 아주 빠른 첫 탭이면 `play()`에서 즉시 실행 |
| 재굴림 물리 준비 앞당기기 | **채택** | 슬라이드가 없으면 착지 40 ms 뒤 준비, 유휴 콜백 타임아웃 250 ms |
| Web Worker 물리 | 보류 | 준비 경로가 대부분을 덮음. 워커로 옮겨도 탭→첫 프레임은 물리 시간만큼 늦어지고 cannon-es 사본·궤적 전송이 추가됨 |
| 물리 분할(프레임별 시뮬레이션) | 불채택 | 결과 눈은 마지막 자세로 면을 재배치해 정하므로 착지 전 결과가 필요 → 분할 재생 불가 |
| 초기 해상도 낮추기 | 불채택 | 측정상 원인이 아니었고 화질만 손해. 기존 적응형(2→1.5→1.25배) 유지 |
| 프레임당 작업량 제한·할당 감소 | 해당 없음 | 굴림 중 프레임 p95 16.7~16.8 ms로 이미 예산 안 |
| 2.5D 대체 | 기존 유지 | 설정 "간단(2.5D)" 그대로 |

## 3. 개선 전후 측정 (에뮬레이션 — **실기기 아님**)

- **도구:** `scripts/measure-dice-perf.mjs` (저장소에 추가, 누구나 재현 가능). `npm run build && node scripts/measure-dice-perf.mjs --trials 8 --cpu 4 --gap 700`
- **환경:** Playwright Chromium 헤드리스, 소프트웨어 GPU(SwiftShader), Pixel 7 에뮬레이션(412×915, DPR 2.625), 품질 "자동", AI 대전. CPU 감속은 CDP `Emulation.setCPUThrottlingRate`.
- **절차(시행마다 새 브라우저 컨텍스트):** 로드 → 설정 → 게임 시작 → 600 ms → 첫 굴림 → (간격) → 2번째 → (간격) → 3번째 → 점수 기록 → AI 턴 → 다음 턴 첫 굴림.
- **비교:** 개선 전 = main `f8dc297` + 동일 진단 필드 패치만, 개선 후 = PR A 성능 커밋. 같은 머신·같은 스크립트, 조건마다 **8회**.
- **원시 데이터:** [docs/ui/perf-2026-11-24/](./perf-2026-11-24/) (before/after × cpu1/cpu4 × gap0/gap700).

값은 8회의 중앙값 [최소–최대], 단위 ms. "최악" = 탭부터 주사위가 멈출 때까지 가장 긴 프레임 간격.

## 5. 주사위 화질·효과음

- **화질:** 2배 캔버스·256 px 면 텍스처·밉맵/비등방성 필터 유지. 그림자 맵 없음(접촉 그림자 평면 1장/주사위), 무광 재질 — 추가로 줄일 비용 없음. 첫 그리기 준비만 개선.
- **효과음 v3 후보(연구실 비교 전용, 기본값 아님):** 순수 사인 대신 아주 짧은 대역 잡음 타격음, 충돌마다 다시 뽑는 비조화 공진비(같은 샘플 반복감 감소), 테이블 몸체음을 휴대폰 스피커가 재생하는 380~520 Hz로 이동(150 Hz 저음은 대부분 휴대폰 스피커에서 사라짐), 주사위끼리 충돌은 3~7 ms 간격 이중 타격(flam), 구르기는 마찰 잡음 + 드문 모서리 틱. 동시 발음 예산·같은 소리 최소 간격·컴프레서는 v2와 공유.
- **실제 음원 샘플 검토:** CC0 녹음(예: Freesound CC0)은 자연스러울 가능성이 크지만 ① 파일·라이선스 출처 관리 ② 다운로드 용량 ③ 충돌 강도별 변형 수가 필요하다. 이번에는 합성 v3를 먼저 비교하고, 사람이 들어 본 뒤 필요하면 샘플 방식을 별도로 진행한다.
- **음질 판단 보류:** 사람이 실제 휴대폰 스피커로 듣지 않았으므로 v3가 더 낫다고 단정하지 않는다. 게임은 계속 v2. 연구실 → 주사위 실험실 → 효과음 시연에서 **이전(v1)·현재(v2)·후보(v3)** 비교.

## 6. 온라인 고정 순서 — Durable Object 재시작 유실 대응

- **문제:** 고정 순서(`hold`)는 행 쓰기를 아끼려고 메모리에만 두고 다음 명령과 함께 저장했다. 고정 토글 후 다음 명령 전에 객체가 비활성화(Hibernation 퇴출)되면, 깨어난 뒤 재접속한 화면은 고정 순서를 잃었다(게임 결과는 영향 없음 — 실제 고정은 굴림 명령이 가져감).
- **해결(쓰기 0회):** 방이 고정 순서를 **모든 소켓의 첨부 데이터(`serializeAttachment`)** 에 매치 버전과 함께 복사한다. 첨부 데이터는 Hibernation 중에도 소켓과 함께 보존되고 SQLite 쓰기가 아니다. 깨어날 때 현재 버전과 같은 가장 최신 사본만 채택한다.
- **보조 복구:** 모든 소켓이 닫힌 뒤 퇴출되면 사본이 없을 수 있다 → 차례인 플레이어 화면은 재접속 시 서버 값이 비어 있고 그 사이 명령이 없었다면 **자기 선택을 다시 공유**한다.
- **검증:** `tests/online-host.test.ts` "고정 순서는 다음 명령 전에 객체가 내려가도…" — 토글 2회에 행 쓰기 0, 퇴출 후 상대 재접속 화면에 같은 순서, 다음 굴림도 그 순서, 오래된 사본 거부.
