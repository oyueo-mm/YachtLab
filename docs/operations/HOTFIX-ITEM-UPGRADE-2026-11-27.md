# 긴급 운영 장애 · 아이템 강화 버튼과 Worker 단계 불일치

사용자 테스트에서 강화가 되지 않는다는 제보가 있었다. 정확한 제보 아이템 ID, 당시 강화 응답 및 사용자 원장은 미확인이다. 기존 보드판을 대상으로 **동일한 증상을 격리 환경에서 재현**했다.

## 운영 버전과 원인

| 운영 근거 | 관측 |
| --- | --- |
| 공개 Pages | `/YachtLab/version.json`이 `ef725f6-mwz0xx5p`를 반환했다. 공개 번들에서 기존 온라인 Worker 주소를 확인했다. |
| Worker 공개 GET | `/healthz` 200, `/api/features` 200에서 `signIn:true`와 `economy:true`, `/api/auth/config` 200에서 `google:true`. |
| GitHub의 최신 성공 Worker 배포 | 소스 `54c13679f04e11c13efd2d0e7d3a7b412d86167b`, 배포 시 로그의 버전 ID `900728c2-c252-4dc7-be9f-0b698826eca7`. 대시보드 배포 및 현재 활성 버전 UUID는 미확인. [수동 배포 로그](https://github.com/oyueo-mm/YachtLab/actions/runs/45772443229) |

현재 Pages는 기존 비기본 보드판에 Lv.2·Lv.3과 강화 비용을 표시한다. 마지막 Worker 배포 기록의 소스에서는 기존 보드판 11종의 최대 단계가 Lv.1이다. 기존 보드 ID의 도입 판은 여전히 1이다. 기존 클라이언트의 `sellableOn`은 신규 상품 판매를 제한하지만 보유한 기존 보드의 새 강화 단계 지원 여부는 검사하지 않았다. 버튼을 누르면 구 Worker는 정상 요청도 `400 MAX_LEVEL`과 “강화할 수 없는 아이템이에요”로 거절한다. 오류는 인벤토리 상세 모달 뒤에 있었고 일반 스냅샷 재조회가 이 오류를 지우기도 했다.

| 기존 보드판 Lv.1→2 / Lv.2→3 | Rev.2 코인 비용 |
| --- | ---: |
| 레드·블루·퍼플·베이지 펠트 | 135 / 270 |
| 그린 펠트·원목·월넛·브라운 가죽·블랙 가죽 | 450 / 900 |
| 네이비·눈 내리는 선착장 | 1,350 / 2,700 |

위 11종은 **기존 상품 중 강화 단계가 확장된 보드판**이다. 이미 강화 가능했던 기존 주사위 및 이모티콘의 서버 단계는 이 차이에 해당하지 않는다. 별도의 **신규 카탈로그 11종**은 구 Worker에 ID가 없으며 주사위 5종과 보드 6종으로 구성된다. `catalogRev`가 없으면 Pages는 1판으로 해석해 신규 상품을 판매 준비 중으로 표시한다. 구 Worker의 신규 ID 강화는 `400 NOT_OWNED`다. 그대로 유지되는 등급·구매·뽑기·강화 가격표는 별도 정책이다.

## API 및 원장 검증

`POST /api/me/shop/upgrade`는 Bearer 세션과 JSON `{itemId, requestId}`를 받는다. 요청 ID는 8~64자의 영숫자·밑줄·하이픈이다. 서버가 세션에 해당하는 계정 객체에서 보유 행·현재 단계·자체 카탈로그·잔액을 검증한다. 결과는 `200 {snapshot, duplicate}`, 인증 없음 `401 UNAUTHENTICATED`, 미보유 또는 모르는 ID `400 NOT_OWNED`, 강화 미지원 또는 최대 단계 `400 MAX_LEVEL`, 잔액 부족 `402 INSUFFICIENT`, 경제 꺼짐 `404 ECONOMY_OFF`다.

`54c1367`과 `main`의 Worker를 분리한 Wrangler SQLite에서 실행했다. 모두 루프백 가짜 OIDC로 로그인하고 테스트 계정에만 합성 잔액·보유품을 넣었다. 운영에는 위 공개 GET만 호출했다.

| 격리 재현 | 결과 |
| --- | --- |
| 구 Worker, 보유한 레드 펠트 Lv.1 | `400 MAX_LEVEL`. 20,200코인, 보유 Lv.1, 강화 원장 0행 그대로 |
| 구 Worker, 신규 초원 보드 | `400 NOT_OWNED`. 잔액·인벤토리·원장 그대로 |

| Rev.2 Worker, 보유한 신규 초원 보드 Lv.1 | `200`. 1,350코인 차감 1회, 강화 원장 1행, Lv.2 저장 |
| 두 Worker, 기존 민트 주사위와 동일 요청 3회 병렬 재전송 | 첫 요청 `200`, 150코인과 Lv.2 적용. 재전송은 모두 `duplicate:true`. 추가 차감·단계 변경 0 |

| 두 Worker, 같은 아이템에 서로 다른 요청 ID 2건 동시 요청 | 둘 다 `200`, 보유 Lv.3 및 150+300=450코인 차감. 두 ID는 별개 승인으로 처리 |
| 두 Worker, 비인증 및 미보유 계정 요청 | `401 UNAUTHENTICATED` 및 `400 NOT_OWNED` 확인 |

강화 차감·원장의 `up:<requestId>`·소유 단계 저장은 같은 SQLite 트랜잭션이다. **재화만 차감되고 보유 단계가 저장되지 않은 경우는 이 격리 테스트에서 재현되지 않았다.** 성공 응답 유실 시 두 변경이 모두 반영돼 있을 수 있다. 브라우저의 자동 네트워크 재시도는 같은 ID를 사용한다. 재시도 뒤 사용자가 새로 확인하거나 다른 탭에서 누를 때는 별개의 ID가 전송되며, 현재 API는 어느 출발 단계에 동의했는지 받지 않는다.

보유 단계와 선택한 장착 단계는 다르다. 낮은 단계를 명시한 장착은 강화 뒤에도 선택값을 사용한다. 새 단계 표시를 명시하려면 선택하고 장착을 저장해야 한다. 선택을 명시하지 않았으면 서버가 보유 단계로 계산한다. 방에서는 생성·입장 때 저장한 외형 스냅샷을 보내므로 이미 참가한 방의 재접속만으로 최신 장착이 갱신되지는 않는다. 이전 렌더러가 모르는 신규 ID나 빠진 단계 필드는 기본 외형·Lv.1로 표시될 수 있다.

## 수정안 및 A2 조율

- 이 Hotfix 브랜치는 Pages에서 판매 판과 강화 지원 판을 별도로 검사한다. 구 Worker가 지원하지 않는 단계는 미리보기와 준비 중 안내만 표시한다. 상세 창에 보유·선택 단계와 API 오류를 표시하고, 재조회 후에도 오류를 유지한다. 성공 응답의 인벤토리에 해당 단계가 있을 때 완료를 표시한다.
- 다음 Worker 수정 후보는 선택적 `expectedLevel`을 받아 같은 SQLite 트랜잭션에서 현재 단계와 대조하는 것이다. 응답 유실 시 원래 요청을 같은 ID로 조회하거나 재시도하는 경로와, 이미 쓰인 요청 ID가 다른 아이템에 연결될 때 거절하는 계약을 함께 정의한다. 현재 브랜치는 Worker 코드와 경제·등급·가격을 그대로 사용한다.
- A2는 인증된 새 방에서 `welcome.looks`의 `dice/diceLv/board/boardLv`를 화면과 대조할 수 있다. 1:1은 본인 보드와 현재 굴린 좌석의 주사위를 사용한다. 다인전과 관전에서는 기존 방 스냅샷과 표시 로직을 구분한다. [A2 PR](https://github.com/oyueo-mm/YachtLab/pull/117)
- 실제 신고 계정, 운영 실기기, 현재 Cloudflare 활성 버전 및 롤백 권한은 미확인이다. 운영 Worker 배포 보류를 유지한다. [C0 운영 점검](https://github.com/oyueo-mm/YachtLab/pull/112)

## 병합·배포 결과 (2026-11-27)

- PR #119를 `74bfcd8`의 PR CI 통과(run 46018302968) 후 main에 병합했다(`fa22a35`). main push CI(run 46035799537)의 unit·build·browser 4샤드가 통과했고 Pages `deploy`가 성공했다. 공개 `version.json`은 `fa22a35-mwz7mtg3`.
- 운영 Worker는 바뀌지 않았다. `/healthz` 200, `/api/features`에 `catalogRev`·C3 플래그가 없다(구 Worker 유지). C0 Worker 배포 보류는 그대로다.
- 비파괴 확인: 운영 Pages 번들에서 `?online-server=` 대체 주소와 브라우저 안의 모의 경제 API로 `tests/ui/economy.spec.ts`의 강화 관련 6건(데스크톱·모바일)을 실행해 통과했다. 기존 보드 Lv.2 강화 버튼이 없고 "준비 중" 안내가 표시되며 요청이 0건, 기존 주사위 강화는 상세 창 오류 표시 후 재시도로 Lv.2가 됐다. 실제 계정·재화·운영 Worker 상태를 바꾸는 요청은 보내지 않았다.
- 이것은 구 Worker 기능 차이를 안내하는 임시 조치다. 기존 보드 Lv.2·3 강화와 신규 카탈로그 판매는 Rev.2 Worker 배포 전까지 열리지 않는다. 다른 요청 ID로 동시에 두 번 강화하면 두 단계가 결제되는 문제(`expectedLevel` 후보)는 남아 있다.
