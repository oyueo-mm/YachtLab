## 현재 구조와 무료 한도

GitHub Pages가 정적 HTML·번들·AI 자산을 제공한다. Worker는 계정·HTTP 라우팅과 WebSocket 업그레이드를 담당한다. 방별 `YachtRoom`이 SQLite에 직렬화된 상태·이벤트를 저장한다. `RoomDirectory`는 방 확인·할당·일일 예산, `MatchHub`는 빠른 대전·공개 관전 목록, `UserStore`는 계정별 세션·경기·경제 원장, `GuestLink`와 `FriendIndex`는 연결·친구 색인을 담당한다. WebSocket Hibernation을 사용하고 관전·채팅의 수신 측 팬아웃은 유료 요청 수를 직접 늘리지 않지만 직렬화와 CPU 비용이 생긴다. ## 시나리오

1:1, 일 2시간 피크, 평균 15분, 같은 활성 CCU 유지, 종료 경기의 새 방 비율 100% 및 30분 잔류를 상한으로 모델링했다. 방당 일반 HTTP·업그레이드 8회(업그레이드 4 포함), DO HTTP/RPC/알람 65회, 수신 앱 메시지 120개, SQLite 읽기 160·쓰기 140행, 열린 방 저장 64KiB, 정산 회원 1명에 24KiB를 가정했다. 과거 문서의 방 쓰기 약 110~120행은 참고치이며 현행 계정 정산과 공개 관전이 포함된 운영 실측이 아니다. ## 확장 순서

1. 첫 행사에는 피크 20명 목표를 둔다. 기존 Cloudflare 대시보드에서 같은 대기 시간대의 방 개수와 생성 예산, HTTP 오류, DO duration·행 쓰기·CPU p95를 함께 기록한다. 공유 한도에 30% 이상 여유를 확보한다는 운영 목표를 둔다.
2. 피크 DO duration가 방당 15초에서 60초로 늘면 표의 duration은 4배다. 1,000 CCU에서 30,720GB-s/일이다. Hibernation 적격 상태, 알람과 재생성 비용, 공용 Hub와 Directory RPC를 먼저 보정한다.
3. 재대결과 빈 방 청소를 개선해 방 수와 생성량을 줄이고, 계정 기록은 기간/크기 기반 정리 및 요약을 먼저 설계한다. 일반 홈 진입과 AI 선택까지 정적 네트워크 비용도 함께 본다. 냉간 방문 0.4MB만으로 약 25만 회에 100GB가 되고, 오프라인 사전 캐시와 AI가 포함되면 더 적은 방문 수에서 도달한다.
4. 100~500 CCU 이후는 지표에 따라 관전 조회 TTL·갱신 빈도, 방 상태 팬아웃, 원장 트랜잭션, 허브 샤딩 순으로 검토한다. 공유 쿼터와 단일 DO 큐 한계는 별도로 검증하고, 공개 전에는 저장 지연 p95와 더 작은 단위의 로컬 실험을 비교한다. 유료 전환 의사결정은 한도와 실제 격리 측정 이후에 한다.
