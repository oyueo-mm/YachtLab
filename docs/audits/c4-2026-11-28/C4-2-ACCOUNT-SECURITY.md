## 2. SEC-03 설계 — 탈퇴와 친구 그래프

### 2.1 친구 코드 = 계정 세대

내부 ID는 `H(provider, sub)`라 재가입해도 같다(`oidc.ts` `userIdFor`). 대신 **친구 코드**는 계정이 살아 있는 동안 바뀌지 않고 탈퇴 때만 폐기된다. 그래서 다른 계정에 저장된 모든 행(친구·받은 요청·보낸 요청·차단·초대)이 만들 때의 코드를 함께 가지며, 계정 간 단계는 이 코드를 대조한다.

- 탈퇴 시 코드는 계정 객체의 `fr_retired`에 남고(30일, 재가입 쿨다운과 함께 삭제), 재가입 계정이 친구 기능을 처음 쓸 때 색인에 `avoid`로 넘긴다 — 색인 정리가 아직 안 끝났어도 **옛 코드를 다시 받지 않는다**(`FriendIndexStore.register`).
- 색인 정리는 `removeCode(id, code)` — 그 세대의 코드일 때만 지우므로 재가입 후 늦게 도착한 재시도가 새 코드를 지우지 않는다.

### 2.2 탈퇴 절차 (`UserStore.deleteAccount`)

1. 같은 이벤트 안에서(다른 요청이 끼어들 수 없음) `deletionPlan()` = 내 코드 + 나에 대한 행을 가진 모든 계정(친구, 받은/보낸 요청, 내가 차단한 상대, 나를 차단한 상대).
2. **한 트랜잭션:** 계정 테이블 전부 DROP(`tomb`·`acct_cleanup`·`fr_retired` 제외), 삭제 시각 기록, 폐기 코드 기록, 대기열 `acct_cleanup`(대상 ID + 폐기 코드)과 소유자 ID 기록. 이전의 `deleteAll()` 후 별도 쓰기와 달리 "지웠는데 정리 목록을 잃는" 창이 없다.
3. 대기열을 즉시 처리(최대 40건/호출 — Workers Free 하위 요청 한도 고려), 남은 것은 알람.
4. 알람: 백오프 1분·5분·15분·1시간·3시간·6시간·12시간·24시간…, 16회(약 9.5일) 실패하면 그 건은 **보류(parked)** — 지표 `account.cleanup.gaveUp`. 재시도는 `account.cleanup.retry`. 보류 건이 있는 계정은 주 1회 운영자 재처리 요청(§8-2)을 확인한다. 대기열이 비면 소유자 ID도 지운다.
5. 30일 뒤 알람: 진행 중 재시도가 없으면 보류 건을 폐기(`account.cleanup.expired`)하고, 계정이 없으면 객체 전체 삭제(기존과 같음).

`forget(id, code)` (상대 계정에서): 그 세대의 친구 행·받은 요청·보낸 요청(거절 대기 행 포함)·초대·차단 역색인 삭제, **내가 그 사람을 차단한 행은 익명화**(닉네임 "탈퇴한 사용자", 코드는 어디에도 등록되지 않은 새 임의 코드 — 차단 해제 버튼용). 멱등.

### 2.3 없는 계정은 아무것도 저장하지 않는다

`UserStore.fr`는 계정 행이 없으면(미가입·탈퇴) 모든 친구 연산에 중립 값을 돌려주고 **쓰지 않는다**(`ABSENT_ACCOUNT`). 이전에는 탈퇴 직후 상대가 보낸 요청·초대·수락이 빈 객체에 `fr_in`·`fr_friends`·`fr_meta`를 새로 만들 수 있었다. 요청 대상 표시 정보도 상대 계정 객체가 아니라 색인에서 읽는다(대상 계정에 코드 발급 쓰기를 하지 않음).

### 2.4 수락·요청 프로토콜과 경합

수락(B가 A의 요청을 수락):

1. B의 `incomingPeer(code)`.
2. **A.`acceptedBy`(B, A의 요청 당시 코드)** — A의 현재 코드가 같고 A가 B에게 보낸 대기 요청(같은 세대)이 있을 때만 A 쪽에 친구 추가. 재가입 A(빈 목록·새 코드)나 탈퇴 A(없는 계정)는 거절 → B는 그 요청 행만 지우고 `404 REQUEST_GONE`.
3. B.`addFriend`(A).
4. **확인:** A가 여전히 B를 같은 세대의 친구로 갖는지 묻고, 아니면 B 쪽을 되돌린다.

경합 분석: A의 탈퇴는 1단계(계획+삭제)가 원자적이므로 2단계는 "탈퇴 전"(그러면 A의 계획에 B가 친구로 들어가 `forget`이 B에 도달) 또는 "탈퇴 후"(거절) 중 하나다. 3단계 뒤에 `forget`이 오면 지워지고, 3단계 전에 `forget`이 와도 4단계 확인이 되돌린다. 작업자가 2~3 사이에 죽으면 A만 친구를 가진 상태가 되지만 B의 요청 행이 남아 같은 수락을 다시 하면 2단계가 멱등으로 통과한다.

요청(B → A): B가 먼저 `recordOutgoing` 후 A.`receiveRequest`. A가 그 전에 탈퇴했으면 "gone" → B가 지움, 그 뒤 탈퇴하면 A의 계획에 B(받은 요청)가 들어간다. 교차 요청으로 친구가 될 때도 같은 확인 단계를 거친다. `receiveRequest`는 같은 사람의 **다른 세대 행**(예: 재가입 전 계정에 보냈던 내 요청)을 동의로 보지 않는다.

### 2.5 초대·접속 상태·거절 행

- 초대 목록은 **같은 세대의 현재 친구**가 보낸 것만(조인), 친구 삭제·차단 시 그 사람의 초대 삭제 → 전 친구·탈퇴자의 초대로 방에 들어갈 수 없다.
- 접속 상태(`presence`)는 묻는 사람이 상대의 친구 목록에도 있을 때만(한쪽에만 남은 행으로 재가입자의 접속 여부를 볼 수 없음). 추가 RPC 없음.
- 거절된 보낸 요청은 닉네임·코드를 비우고 시각만 남겼다가 24시간 뒤 다음 요청 때 삭제.

### 2.6 차단 (개인정보 최소화 + 회피 방지)

- 차단하면 상대 계정에 서버 전용 역색인 `fr_blocked_by(차단자 ID, 차단자 코드)`가 생긴다(클라이언트에 절대 반환 안 함, 차단 사실 비공개 원칙 유지). 차단 해제 시 삭제. 어느 쪽이 탈퇴해도 상대 쪽 정리 경로가 생긴다.
- 차단된 사람이 탈퇴 → 차단자 목록은 "탈퇴한 사용자"(닉네임·친구 코드 없음) + 내부 ID·시각만. 같은 Google 계정으로 재가입해도 내부 ID가 같으므로 **차단이 계속 적용**되고(요청은 "보냄"처럼 보이지만 전달되지 않음), 차단자는 언제든 해제할 수 있다. 내부 ID(가명 해시)를 남기는 이유는 차단 회피 방지라는 차단자 보호 목적이며, 차단자가 해제하거나 탈퇴하면 사라진다(D-C42-2).
- 차단한 사람이 탈퇴 → 상대의 역색인 삭제.

## 3. SEC-04 설계 — 세션

| 시점 | 동작 | 비용(Workers Free) |
|---|---|---|
| 로그인(`exchange`) | 만료 세션·로그인 코드 일괄 삭제 → 상한 적용 → 새 세션 → 알람이 없거나 더 늦으면 다음 만료+1분으로 | 행 읽기 ≤ 20, 알람 읽기 1·쓰기 ≤ 1 |
| 인증(`authenticate`) | 객체 메모리 기준 하루 1회 일괄 삭제(기존 "그 세션이 만료면 삭제"도 유지) | 하루 1회 소량 읽기 |
| 계정 알람 | 만료 정리 후 다음 만료·정리 재시도·재가입 쿨다운 중 가장 이른 시각으로 재설정(알람 1개 공유) | 계정당 대략 30일에 1회 |
| 상한 | 유효 세션 20개 초과분은 가장 오래된 것부터 종료 | — |

- **기존 유효 세션 유지:** 배포 자체는 어떤 세션도 끝내지 않는다. 상한은 이미 20개 이상인 계정이 *새로 로그인할 때만* 가장 오래된 것을 끝낸다(30일 안에 20회 이상 새 로그인은 매우 드묾).
- **유지:** 토큰 형식·TTL 30일·회전 없음·localStorage, `logout`(현재 세션)·`logout-all`(전체), OAuth 흐름, 탈퇴 시 세션 전부 삭제. 토큰 체계 변경(짧은 접근 토큰+회전)·기존 세션 강제 만료(SEC-01 확인 후 회전 등)는 **별도 승인 대상**으로 남김.
- **한계:** 배포 전에 마지막으로 로그인하고 다시 오지 않는 계정의 만료 행은 알람이 없으므로 그 계정이 다시 요청할 때까지 남는다(값은 SHA-256 해시라 재사용 불가). 전역 계정 목록이 없어 일괄 순회는 불가 — 필요하면 관리자 RPC로 별도 설계(승인 대상).

## 4. 이미 탈퇴한 계정의 잔존 데이터 — 안전한 정리 설계 (운영자 승인 전 미적용)

**대상:** 이 변경 전에 탈퇴한 계정이 다른 회원 목록에 남긴 행(받은/보낸 요청, 한쪽만 지워진 친구, 차단 목록의 닉네임·코드).

**판정(2단계):** ① 사전 필터 — 행의 (내부 ID, 친구 코드)가 전역 색인 `codes`에 없으면 후보. ② 확인 — 후보마다 **그 계정 객체 자신**(자기 세대의 권위)에 현재 코드를 묻고, 계정이 없거나 코드가 다를 때만 잔존으로 판정. 계정이 그 코드를 아직 가지면 색인 결함으로 보고 **건드리지 않고** `friends.residue.indexMismatch`로만 센다. 그래서 색인이 통째로 없어지거나 손상돼도 정상 계정의 친구 관계는 지워지지 않는다(§8-1, 테스트·변이 검사). 확인은 1회 최대 50건.

**방식:** 일괄 작업이 아니라 각 회원이 친구 목록을 열 때, 그 계정 객체가 하루 최대 1번 색인에 한 번 묻는다(`FriendIndex.live`, 최대 1000쌍). 비용: 친구 화면 조회당 전역 DO 호출 1회 추가(하루 1회 한도).

| `FRIEND_RESIDUE_CLEANUP` | 동작 |
|---|---|
| 없음/`off` (기본) | 아무것도 하지 않음 |
| `dry-run` | 발견 개수만 Hub 지표 `friends.residue.found`(+ `indexMismatch`)와 앱 로그 `FRIEND_RESIDUE`에 기록(ID 없음), 데이터 변경 없음 |
| `on` | 확인된 행에 `forget` 적용(차단은 익명화) + `friends.residue.cleaned` — **미승인** |

**운영 절차(승인 필요):** ① 이 PR 배포 후에도 `off` 유지 → ② 별도 승인 시 `dry-run`으로 7일 관찰: `friends.residue.found`(예상 규모인지), `friends.residue.indexMismatch`(0이어야 함 — 0이 아니면 색인 점검 전 `on` 금지) → ③ (미승인) `on` → ④ 목표 기간 뒤 `off`. 관찰 방법은 §8-6. 되돌리기: 변수를 `off`로(즉시). `on`으로 지운 행은 되돌릴 수 없으므로 `dry-run` 단계를 건너뛰지 않는다. 전역 색인 손상·복구 직후에는 `on`을 켜지 않는다(색인에 없는 = 탈퇴로 판정하기 때문).

**한계:** 구버전 탈퇴 때 색인 삭제마저 실패한 계정은 탐지되지 않음(드묾). 친구 화면을 열지 않는 회원의 잔존 행은 남음. 구버전 차단에는 역색인이 없어 이후 탈퇴 시 `on`일 때만 익명화.

**플래그와 무관하게 이미 적용되는 것(개별 사용자 행동에 따른 해당 행 처리):** 수락을 시도한 죽은 요청 1행 삭제, 재가입한 같은 사람이 다시 연락했을 때 그 사람의 옛 세대 행 교체, 친구가 아닌 사람의 초대 미표시(읽기 시점), 한쪽만 남은 친구 행으로 접속 상태 미노출(읽기 시점). 일괄 수정은 없다.

## 6. 운영 반영 조건 (승인 대상)

## 8. 최종 검증 6항목 (2026-11-27 운영자 요청)

### 8-1. 전역 친구 색인 누락·손상 시 정상 계정의 친구 관계가 삭제될 위험

| 경로 | 색인에 의존? | 결과 |
|---|---|---|
| 탈퇴 정리(`forget`) | 아니오 — 탈퇴 계정 자신의 목록 + 세대 코드 | 영향 없음 |
| 수락(`acceptedBy`)·교차 요청·초대·접속 상태 | 아니오 — 양쪽 계정 객체가 판단 | 영향 없음 |
| 요청·차단 대상 찾기, 검색, 프로필 | 예(조회만) | 색인이 없으면 "찾을 수 없음" — **삭제 없음** |
| 잔존 정리(`FRIEND_RESIDUE_CLEANUP`) | 사전 필터로만 | 수정 전에는 색인 손실 = 전부 탈퇴로 판정될 위험이 있었음 → **계정 객체 확인 단계 추가**로 제거. 색인 전체 삭제·다른 계정을 가리키는 손상 모두 테스트(`on` 모드)에서 정상 친구·요청·차단 보존, `indexMismatch`로만 집계. 확인 단계를 빼는 변이에서 테스트 2건 실패 |
| 색인 재등록 | — | 닉네임 변경 시 색인 항목이 없으면 **같은 코드로 복구**(이전에는 새 코드를 만들어 세대가 바뀔 수 있었음) |

남은 위험: 색인이 손실되면 친구 코드 검색·요청이 그 계정의 다음 닉네임 변경 때까지 안 된다. 데이터는 삭제되지 않는다.

### 8-2. 삭제 재시도를 모두 실패한 경우의 안전한 재처리

- 16회 실패 건은 삭제하지 않고 **보류**한다(`account.cleanup.gaveUp`).
- 재처리 절차(신규 관리자 기능 없음, Worker 설정만 사용):
  1. 원인(상대 DO·색인 장애)을 해결한다.
  2. **`ACCOUNT_CLEANUP_RETRY_EPOCH`를 새 값(예: `2026-12-01`)으로 승인 배포**한다.
  3. 보류 건이 있는 각 계정이 주 1회 이 값을 확인한다. 바뀐 값을 보면 보류 건을 활성으로 되돌려 다시 최대 16회 시도한다(`account.cleanup.requeued`).
  4. 같은 값으로는 다시 처리하지 않는다.
- 안전성: 모든 단계는 멱등이고 탈퇴한 세대로 한정된다. 재가입 이후에 다시 돌려도 새 관계를 건드리지 않는다(8-3 테스트).
- 시한: 탈퇴 후 30일 기록이 끝날 때 보류 건은 폐기된다(`account.cleanup.expired`). 그 이후의 잔존 정보는 상대 회원 쪽 잔존 정리(§4, 승인 대상)가 유일한 경로다.
- 테스트: 보류 → 같은 epoch 무시 → 새 epoch 재처리 성공 → 다시 보류 → 폐기.

### 8-3. 재가입과 이전 계정의 정리 알람이 동시에 실행되는 경우

- 한 계정 객체는 이벤트를 하나씩 처리하고, RPC를 기다리는 동안에만 다른 이벤트가 끼어든다.
- 정리는 옛 코드로만 지운다(`forget(id, 옛 코드)`, 색인 `removeCode(id, 옛 코드)`). 재가입 계정은 친구 기능을 처음 쓸 때 옛 코드를 피해 새 코드를 받는다(`fr_retired` → `avoid`). 그래서 늦게 도착한 정리가 새 요청·친구·코드를 지울 수 없다.
- 대기열의 소유자 ID와 재시도 상태는 재가입으로 바뀌지 않는다. 재가입 후 다시 탈퇴하면 (대상, 코드) 키로 두 세대의 작업이 따로 쌓인다.
- 테스트(전수): "재가입 → 요청 → 수락" 흐름의 모든 RPC 사이에 옛 세대 재시도를 끼우고, 반대로 재시도의 각 `forget` 호출 사이에 그 흐름 전체를 끼웠다. 두 방향 모두에서 새 친구 관계·새 코드가 보존되고, 옛 세대 행·옛 색인 항목은 모두 정리되며, 대기열은 비었다.
- 함께 고친 결함: 30일 기록 종료 시점에 백오프 중인 재시도가 남아 있으면 알람이 매초 다시 울릴 수 있었다. 지난 종료 시각은 일정에서 빼도록 수정했다.

### 8-6. 운영 `ADMIN_TOKEN` 미등록 상태에서 정리 지표 확인

- 정리 관련 숫자는 Hub 지표(`/api/admin/metrics`, ADMIN_TOKEN 필요)와 함께 **ID 없는 앱 로그 한 줄**로도 남긴다.
  - `ACCOUNT_CLEANUP {"retry":n,"gaveUp":n,"remaining":n}` / `{"requeued":n}` / `{"expired":n}`
  - `FRIEND_RESIDUE {"friends.residue.found":n}` 등
- 확인 방법(새 관리자 기능 없음):
  1. Cloudflare 대시보드 → Workers → 해당 Worker → Observability(Logs)에서 `ACCOUNT_CLEANUP` / `FRIEND_RESIDUE`로 검색. C4.1 #123은 호출 로그만 끄고 앱 로그(`console.*`)는 켜 둔다.
  2. 운영자 PC에서 실시간 확인:

```bash
npx wrangler tail yachtlab-online --search ACCOUNT_CLEANUP
```

- 한계: Workers Logs는 3일 보관이다. 7일 dry-run 관찰은 최소 2~3일 간격으로 대시보드를 확인하거나, 기존 기능인 `ADMIN_TOKEN`을 등록해 Hub 지표(일 단위 누적)로 본다. 로그 줄은 발견 건이 있을 때만 남아 로그 한도(무료 20만/일)에 영향이 거의 없다.
