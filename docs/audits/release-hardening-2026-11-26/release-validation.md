## 첫 화면과 오프라인

튜토리얼에서 높이를 고정한 주사위판과 정적 DOM 주사위를 먼저 렌더링한다. 첫 굴림을 한 번만 예약하고, 물리 렌더러 배치가 끝나면 같은 Cannon·Three 주사위판에서 실행한다. 설정 화면에서 필요할 때만 WebGL 기능을 탐지한다. 기본 로비의 선행 로딩은 실제 포인터·키 입력 뒤 idle에서 실행한다. 연습 모드에서는 기존처럼 먼저 물리판을 준비한다. 기준 및 후보 빌드의 물리 테이블과 스테이지 번들 SHA-256은 각각 일치했다. 게임에 직접 들어와 모듈이 아직 준비되지 않은 경우 굴림 입력과 로컬 AI는 물리판이 준비될 때까지 기다린다. 모션 감소와 WebGL·가져오기 실패 시 기존 DOM 렌더러로 진행한다. 물리판 준비에 12초가 걸리면 DOM 렌더러로 전환한다. 킵 선반은 장식 요소로 숨기고, 주사위 버튼의 키보드 동작과 이름을 유지했다.

HTML 셸 외 PWA 필수 캐시 목록은 22개에서 13개가 됐다. 3D 테이블·스테이지와 DP 데이터, 기본 AI 워커는 설치 시 캐시에 넣는다. 복기·상점·연구실의 선택 번들은 같은 빌드에서 처음 사용하면 캐시에 넣는다. 첫 설치 시 선택 번들이 오프라인에서 자동 확보되던 동작은 바뀌었다. 로컬 서버의 콜드 로드 총 전송 본문은 중앙값 2,183,513 → 2,120,256바이트였다. 앱 JS/CSS 전송량은 비슷하고, 전송량 감소 대부분은 PWA 사전 캐시에서 나왔다. Lighthouse의 부트업 목록에서 3D 테이블의 실행 비용이 첫 화면에서 사라졌지만 3D 자원 요청은 필수 사전 캐시에 남는다.

Lighthouse TBT와 위 상호작용 시간은 현장 INP와 별개다.

재현은 main과 PR을 별도 체크아웃해 같은 Node에서 `npm run build`를 실행한다. 각각의 `dist/`를 프로파일 디렉터리의 `baseline/`과 `candidate/`로 복사하고, 같은 디렉터리의 `build-context.json`에 `{"variants":["baseline","candidate"]}`를 쓴다. `YACHT_LIGHTHOUSE_ROOT`를 Lighthouse 13.6.0 설치 경로로 지정한다. 모바일은 기본 명령, 데스크톱은 `YACHT_DESKTOP=1`을 붙여 실행한다. ## 브라우저 회귀와 PWA 업데이트

홈의 자동 3D 캐시 요청을 기다리던 검사는 게임으로 진입해 실제 캔버스를 기다리도록 바꿨다. 3D 파일 응답을 지연한 테스트에서 첫 굴림은 물리판 초기화 뒤 작동했다. 족보 검사는 점수 클릭 이전부터 브라우저 프레임을 기록하므로 모바일 다이얼로그가 닫히는 동안의 연출도 관측한다. 1920×1080 초대 테스트는 호스트 대기실의 6자리 코드가 표시된 뒤 읽는다.

동일한 로컬 오리진에서 구 버전과 신 버전을 차례로 제공했다. 이전 탭을 닫기 전에는 양쪽 캐시를 확인했고, 새 워커 활성화 뒤에는 새 캐시만 남았다. 네트워크를 끈 뒤에도 연습 첫 굴림이 3D였다. [버전 전환 재현](verify-pwa-update.mjs)

## 서버 AI와 요청 제한

승인된 서버 AI의 정책과 카테고리 우선순위를 유지한다. 한 결정에서 같은 최종 눈 조합의 점수를 한 번 계산하고, 조합별 확률과 기존 비교 순서를 유지한다. 동일한 306개 결정이 이전 구현과 일치했다. 워밍업 뒤 스레드 CPU를 3회 교차 측정한 평균은 기존 2.49·2.54·2.80ms, 변경 0.47·0.49·0.48ms다. p99 중앙값은 8.01 → 4.02ms다. Node CPU 수치이고 외부 서비스 호출, 프로덕션 Workers 벽시계 시간과 DO 전체 CPU는 포함하지 않는다. 기존 Vitest 평균 3ms·p99 8ms 기준은 유지하고 측정 대상만 스레드 CPU로 바꿨다. [AI 측정 데이터](server-ai.json) · [비교 스크립트](../followup-2026-11-26/compare-server-ai.mjs)

요청 제한 회귀 테스트는 고정 시간 후 소켓을 읽는 대신 실제 close 이벤트를 기다린다. HTTP 429 및 WebSocket 1008·1009 기준은 기존과 같다. 제품 요청 제한 값은 그대로다.

## 종료 방과 재대결

접속자가 결과 화면에 남은 방의 유휴 정리를 60분에서 10분으로 줄였다. 모두 나간 종료 방은 3분, 경기 중 재접속 유예는 2분이다. 이전 경기의 기보·보상이 계정에 저장되었음을 확인할 때까지 DO의 영속 결과 큐를 보존해 ACK 유실이나 장애 뒤 재시도한다. 계정 기록은 경기 ID로 멱등 처리한다. 이미 접수된 재대결은 방 정리와 같은 직렬 큐에서 처리하며 기존 코드와 승인된 좌석을 사용하고 새 경기 ID를 부여한다.

하루 기본 300단위·동시 방 50개와 기존 AI 하위 예산을 유지한다. 첫 방이 1단위, 이후 인원에 맞춘 첫 대국 추가분 및 재대결은 경기 번호별로 예약한다. 방 저장이 실패해 시작을 다시 시도해도 이미 예약한 단위는 다시 차감하지 않는다. 재시도에서 인원이 늘면 차이만 예약하며 줄었을 때는 환급을 계산하지 않는다. 이 보수적 정책은 실패 누적에 따른 예산 소진을 줄이면서 일일 한도를 보호한다. 추가 SQLite 비용은 예약을 처음 성공하거나 늘릴 때 행 1개 쓰기와 방 정리 시 예약 삭제다.

40경기/시간 중 절반이 결과 화면에 계속 남는다고 가정하면 기존보다 평균 약 16.7개의 방 슬롯이 빨리 반환된다. 이 값은 `20 × (60−10)/60`으로 계산한 정상 상태 추정이며 실제 동시 접속 수용량은 트래픽과 결과 화면 행동에 따라 달라진다. 정산 지연이 병목이면 적체량과 가장 오래된 보류 건을 먼저 관찰한다. 운영 한도에 접근할 경우 유휴 방, 매치 단위, SQLite 사용량을 각각 관찰한 뒤 조정한다.
