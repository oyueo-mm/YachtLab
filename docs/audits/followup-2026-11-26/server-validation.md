# 서버 AI와 연결 제한 회귀

## 서버 AI

기존 보통 AI는 가능한 킵과 다음 굴림을 전개한다. 서로 다른 킵/굴림 조합이 같은 최종 주사위 멀티셋에 도달해도, 그때마다 빈 카테고리를 다시 만들고 여러 번 같은 점수를 계산했다. 눈이 모두 다른 다섯 개의 주사위에서는 1,682개 킵·굴림 경로가 최대 252개 서로 다른 최종 멀티셋으로 합쳐진다. Node의 스레드 CPU 사용량 기준으로도 이 비용이 관측됐다. 후보는 카드를 한 번 읽고, 각 결정 내부에서 3비트 눈별 개수 키를 사용해 최적 점수를 재사용한다. 다섯 개 주사위는 자리 간 carry가 없고, 기존 전개 순서·확률·부동소수점 합과 동점 기준은 동일하다. 결정의 입력은 자기 주사위·남은 굴림·점수표다. [변경 코드](../../../src/online/server-ai.ts)

| 자체 306개 입력, 세 회차의 중앙값 | 원본 | 후보 |
|---|---:|---:|
| Node 스레드 CPU 평균 | 2.435ms | 0.495ms |
| Node 스레드 CPU p99 | 8.003ms | 4.017ms |
| 회차별 최대 CPU 범위 | 9.242–15.152ms | 4.086–7.999ms |
| 기존 선택과 동일 | 기준 | 306/306 |

입력에는 빈 카드, 눈이 모두 다른 손, 모두 같은 손, 1·2·3번째 굴림이 포함됐다. 측정 앞에 선택 일치 비교를 했으므로 위 표는 워밍업 후 계산 비용이다. CPU 표본에는 약 4ms 단위의 계측 양자화가 보였다. 그보다 작은 차이는 유효숫자로 해석하지 않는다. 전체 Worker 요청 처리, SQLite, 직렬화와 Cloudflare 실제 CPU 한도를 포괄하는 수치는 아니다. 기존 평균 <3ms와 p99 <8ms 검사는 같은 값으로 두었다. [벤치 실행기](compare-server-ai.mjs), [표본](evidence/server-ai.json), [기존 게이트](../../../tests/online-ai.test.ts)

**판정** 제품 계산 중복은 확인했고 최적화로 줄었다. 운영 Free CPU 초과 여부는 Node 수치만으로 판정할 수 없다. Worker/DO CPU 진단에서는 콜드 최초 결정과 전체 메시지·알람 경로를 계측한다.

## 요청·메시지 제한

초기 감사에서 실패한 두 기존 테스트는 종료 코드 불일치 대신 closed가 아직 설정되지 않았다고 보고했다. 요청과 테스트 클라이언트의 비동기 종료 이벤트 사이에 고정 50–300ms만 경과시키고 상태를 읽는 구조였다. 동일한 로컬 회귀의 입력·종료 예상값으로 이미 도착했거나 실제 도착할 close 이벤트에서 판정하도록 바꿨다. 정해진 제한 안에 종료가 없거나 코드가 틀리면 실패한다. 관련 5개 파일은 Node와 로컬 Wrangler를 포함해 55/55 통과했다. 이전 실패를 서비스 보안 취약점으로 판정할 근거는 없으며, 이 수리는 테스트 동기화 문제를 겨냥한다. ## 튜토리얼 접근성

킵 선반 div는 상호작용이 없는 시각 자리 표시이며 실제 주사위 버튼은 형제 요소다. 지원되지 않는 aria-label을 없애고 시각 슬롯만 aria-hidden으로 처리했다. axe의 해당 규칙은 킵 선반 1건에서 패치 0건으로 줄었다. 두 빌드 모두 이름으로 실제 주사위 버튼을 찾고 첫 굴림→첫 킵→aria-pressed=true를 확인했다. 3D 브라우저 회귀는 선반의 장식 속성과 킵 버튼의 접근 가능한 상태를 함께 검사한다. 실제 VoiceOver/TalkBack 발화는 미검증이다.
